## Story

**As a** gestor de tráfego operando contas reais de clientes via CLI,
**I want** um comando `google-ads create audience-custom-segment` que cria um `custom_audience` (segmento de interesse personalizado, definido por palavras-chave e/ou URLs) na conta do Google Ads,
**so that** eu possa alcançar pessoas com interesses/intenções específicas de compra relevantes ao cliente — sem depender de quem já visitou o site (diferente do remarketing da Story 9.1) — direto pelo terminal.

## Context

Terceira story do **Epic 9 — Google Ads Audiences**. Ver `docs/stories/epics/epic-9-google-ads-audiences/EPIC.md` para visão completa do épico.

**Independente de 9.2:** esta story não depende da Story 9.2 (aplicar público) nem da 9.1 (remarketing) para ser implementada — cria uma entidade nova e autocontida (`custom_audience`). Para o segmento criado aqui **produzir alcance em uma campanha**, ele eventualmente precisa ser aplicado a uma campanha/ad group da mesma forma que uma `user_list` — mas isso é reuso natural do mecanismo da Story 9.2 (ou uma extensão futura dela, já que `custom_audience` usa `ad_group_criterion.custom_audience`, um campo irmão de `user_list` no mesmo criterion), não parte desta story.

**Diferença central vs Story 9.1 (remarketing):** `custom_audience` **não é** `user_list`. `user_list` (Story 9.1) é definida por **comportamento no site do cliente** (quem visitou, coletado pela tag). `custom_audience` (esta story) é definida por **sinais de interesse/intenção declarados** — palavras-chave que a pessoa pesquisa, URLs que ela navega, apps que usa — via `CustomAudienceService`, independente de qualquer tag instalada. É o substituto moderno do antigo "custom affinity/custom intent audience" da API.

**Confirmado nos types instalados do SDK v23 (não assumido):** `customer.customAudiences.create(customAudiences, options)` existe como atalho tipado (`node_modules/google-ads-api/build/src/protos/autogen/serviceFactory.d.ts`), alternativo ao `mutateResources` genérico. A entidade `ICustomAudience` (`node_modules/google-ads-node/build/protos/protos.d.ts`) tem os campos: `name`, `description`, `type` (`CustomAudienceTypeEnum.CustomAudienceType`: `AUTO | INTEREST | PURCHASE_INTENT | SEARCH`, todos confirmados no enum instalado), `status` (`CustomAudienceStatusEnum`: `ENABLED | REMOVED`) e `members: ICustomAudienceMember[]`. Cada `ICustomAudienceMember` tem `member_type` (`CustomAudienceMemberTypeEnum`: `KEYWORD | URL | PLACE_CATEGORY | APP`, confirmado) e exatamente um dos campos `keyword`, `url`, `place_category`, `app` preenchido conforme o `member_type`.

**O que NÃO faz parte desta story:**
- Aplicar o `custom_audience` criado a uma campanha/ad group (reuso do mecanismo da Story 9.2, quando/se essa extensão for demandada — não implementado aqui)
- Criar `user_list`/remarketing (Story 9.1, já Done) ou Customer Match (Story 9.4)
- Membros do tipo `PLACE_CATEGORY` ou `APP` (a story cobre `KEYWORD` e `URL`, os dois mais úteis para o caso de uso do usuário — categoria de local e app ficam para evolução futura sob demanda, evitando over-engineering)
- Edição/remoção de custom segments existentes (fora de escopo; só criação)
- Sugestão automática de palavras-chave/URLs para o segmento (isso seria integração com Epic 7 — keyword research — fora de escopo desta story)

## Complexity Estimate

| Métrica | Valor |
|---------|-------|
| T-shirt size | **M** (Medium) |
| Story points (Fibonacci) | **5** |
| Estimativa de tempo @dev | 2.5-3.5h |
| Risk-adjusted upper bound | 5h (se o shape de `ICustomAudienceMember` exigir tratamento adicional não previsto, ou se `type` INTEREST/PURCHASE_INTENT tiver restrições de campos não documentadas) |

**Justificativa:** Entidade nova, mas mais simples estruturalmente que `user_list` rule-based (sem regra aninhada tipo `FlexibleRuleUserListInfo`; `members` é um array plano). Reusa o esqueleto de comando integralmente. Pontuação um pouco acima de 9.1/9.2 pela necessidade de suportar dois tipos de member (`KEYWORD` e `URL`) com parsing de listas via flag (`--keywords "a,b,c"`).

## Acceptance Criteria

1. Novo subcomando `google-ads create audience-custom-segment` registrado sob o comando `create` existente, via `registerAudienceSubcommands` (estendendo `src/cli/commands/audience.ts`, mesmo padrão de `audience-remarketing`).
2. O comando aceita as flags:
   - `--name <text>` (obrigatório) — nome do segmento (max 255 chars, reusar `validateAudienceName` de `audience-validator.ts`)
   - `--description <text>` (opcional) — descrição
   - `--keywords "a,b,c"` (opcional) — lista separada por vírgula de palavras-chave que viram members do tipo `KEYWORD`
   - `--urls "x,y"` (opcional) — lista separada por vírgula de URLs que viram members do tipo `URL`
   - **Pelo menos um** entre `--keywords`/`--urls` deve resultar em ≥1 member válido após parsing (erro PT-BR caso contrário, R4)
   - `--type <AUTO|INTEREST|PURCHASE_INTENT|SEARCH>` (opcional, default `INTEREST`) — validado contra a lista fechada confirmada no enum do SDK
   - `--customer-id <id>` (opcional — default via `getDefaults()`)
   - `--login-customer-id <id>` (opcional — para contas sob MCC)
   - `--dry-run` (opcional, default `false`) — `validate_only: true`
3. O comando monta o(s) `ICustomAudienceMember` a partir de `--keywords`/`--urls` (um member por item, após parsing/trim/remoção de vazios) e cria o `custom_audience` com `name`, `description?`, `type`, `members`. Shape confirmado contra os types instalados do SDK v23 antes de codar (R1).
4. Antes de criar, o comando exibe um **preview** legível em PT-BR com: nome, descrição (se houver), tipo, lista de keywords e/ou URLs que formarão os members, customer-id de destino.
5. O comando exige **confirmação explícita** do operador antes de executar a mutação real (reusar `requireSimpleConfirm`); em `--dry-run`, a confirmação ainda é solicitada mas nenhuma mutação real ocorre.
6. Se o operador cancelar a confirmação, o comando encerra sem erro (exit 0) e registra a tentativa cancelada no mutation-log.
7. Após criação bem-sucedida (real, não dry-run), o comando registra uma entrada em `appendMutationLog` com uma nova operação de auditoria (`create_audience_custom_segment`, adicionada ao union `MutationOperation`).
8. **Tratamento de erro:** falhas de API exibidas em PT-BR via `printError`/`error-map.ts`; fallback genérico se o código não estiver mapeado (mesmo padrão de 9.1/9.2).
9. **Validação client-side:** nome (≤255 chars, reuso de `validateAudienceName`), pelo menos um member válido (R4), `--type` dentro da lista fechada (R5), parsing tolerante a espaços/vazios em `--keywords`/`--urls` (R3).
10. **Boundary rule respeitada:** toda chamada ao SDK `google-ads-api` para esta feature fica isolada em `src/google-ads-api/` (ex.: `custom-segment.ts`, novo módulo); `src/cli/commands/audience.ts` não importa o SDK diretamente.
11. Ao concluir com sucesso, a saída mostra o `resource_name` do `custom_audience` criado, a contagem de members criados por tipo, e uma seção de "próximos passos" em PT-BR mencionando que o segmento precisa ser **aplicado a uma campanha/ad group** para gerar alcance (referência textual à Story 9.2 — mesmo mecanismo de `campaign_criterion`/`ad_group_criterion`, agora via `custom_audience` em vez de `user_list`; sem implementar a aplicação nesta story).
12. Testes unitários (≥80% cobertura nos arquivos de lógica pura novos):
    - Validador de inputs (nome, parsing de keywords/urls, pelo menos um member, `type` válido) — puro
    - Builder que monta o `MutateOperation<resources.ICustomAudience>` a partir dos members — puro, cobrindo apenas keywords, apenas urls, e ambos
    - Formatter do preview — puro
    - Handler do comando com SDK mockado (`getCustomer`/`mutateResources` ou `customAudiences.create` espionado), cobrindo: sucesso, cancelamento, dry-run, erro de API, validação (zero members)
