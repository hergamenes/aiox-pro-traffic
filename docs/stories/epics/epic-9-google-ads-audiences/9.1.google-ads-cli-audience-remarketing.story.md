## Story

**As a** gestor de tráfego operando contas reais de clientes via CLI,
**I want** um comando `google-ads create audience-remarketing` que cria uma lista de remarketing rule-based (`user_list`) na conta do Google Ads,
**so that** eu possa configurar a base de remarketing de um cliente diretamente pelo terminal — sem abrir a UI do Google Ads — aproveitando a tag que já está instalada e coletando visitantes nos sites dos clientes.

## Context

Primeira story do **Epic 9 — Google Ads Audiences**. Ver `docs/stories/epics/epic-9-google-ads-audiences/EPIC.md` para visão completa do épico (4 stories: remarketing → aplicar público → custom segment → Customer Match).

**Confirmado por varredura antes de escrever esta story:** o pacote `packages/google-ads-agent` (v0.1.2) **não possui nenhum código de audiences** — `grep -rn "user_list|UserList|remarketing|audience" src/` (excluindo testes) não retornou nenhuma ocorrência relevante de domínio. Esta é uma capacidade inteiramente nova.

**Pipeline dos épicos anteriores:**
- **Epic 5 (Done)** — CLI que **lê** performance
- **Epic 6 (Done)** — CLI que **muta** campanhas/ad groups/ads/keywords (padrão: preview → confirm → mutate → audit log)
- **Epic 7 (Ready for Review)** — CLI que **pesquisa demanda** (keyword research, read-only)
- **Epic 9 (esta)** — CLI que **cria públicos-alvo** — primeira mutação do domínio de audiences

**Diferença crítica vs qualquer comando existente:** esta é a primeira entidade do tipo `user_list` no pacote. Não existe builder, validator, nem tipo prévio para audiences — tudo é CREATE novo (não há artefato reusável de audiences ainda; REUSE se aplica apenas à infraestrutura de comando — auth, preview/confirm, mutate, audit — não ao domínio).

**Caso mais simples primeiro (evitar over-engineering):** a story cobre a regra de remarketing mais básica e universalmente útil — **"todos os visitantes do site"** — via `rule_based_user_list`. Regras mais específicas (por página, por evento) ficam para evolução futura sob demanda; não fazem parte desta story.

> **Nota (emenda 0.1.2):** o Google Ads exige que toda rule-based user list tenha uma regra baseada na URL da página visitada (variável reservada `url__` + operador de string) — não existe a opção "sem filtro / qualquer pessoa". Portanto **"todos os visitantes do site"** é implementado como o curinga `url__ CONTAINS "http"`, que é o comportamento default quando a flag `--url-contains` (ver AC#2) é omitida. Ver AC#3 para o shape exato da regra.

**O que NÃO faz parte desta story:**
- Aplicar a lista criada a uma campanha/grupo de anúncios (Story 9.2)
- Custom segment / público de interesse (Story 9.3)
- Customer Match / upload de dados de CRM (Story 9.4)
- Regras de remarketing granulares (por URL específica, por evento de conversão) — só "todos os visitantes" nesta story
- Edição/remoção de listas existentes (fora de escopo; só criação)

## Acceptance Criteria

1. Novo subcomando `google-ads create audience-remarketing` registrado sob o comando `create` existente (mesmo padrão de `create campaign-search`, `create campaign-display`, `create campaign-pmax`).
2. O comando aceita as flags:
   - `--name <text>` (obrigatório) — nome da lista (max 255 chars, mesmo limite documentado para `campaign-search --name`)
   - `--description <text>` (opcional) — descrição da lista
   - `--url-contains <texto>` (opcional) — trecho de URL que define quem entra na lista (ex.: o domínio do cliente, `"medicalspin.com.br"`). Quando omitido, a lista usa uma regra curinga que captura qualquer visitante do site (URL contém `"http"`).
   - `--membership-days <n>` (opcional, default `540`) — duração de associação em dias; validação client-side rejeita valores `<= 0` ou `> 540` com mensagem PT-BR indicando a faixa aceita
   - `--customer-id <id>` (opcional — usa default do config via `getDefaults()`)
   - `--login-customer-id <id>` (opcional — para contas sob MCC)
   - `--dry-run` (opcional, default `false`) — não cria nada real, apenas valida (`validate_only: true`)
3. O comando cria a lista como uma rule-based user list cuja regra é: "visitou uma página cuja URL **contém** `<valor>`", onde `<valor>` é o texto de `--url-contains` quando informado, ou o curinga `http` quando omitido (captura todos os visitantes do site). A regra é montada via `FlexibleRuleUserListInfo` (operando inclusivo com `UserListRuleInfo` → `rule_item` na variável `url__`, operador `CONTAINS`). Confirmado nos types instalados do SDK v23.
4. Antes de criar, o comando exibe um **preview** legível em PT-BR com: nome, descrição (se houver), duração de associação em dias, customer-id de destino — seguindo o mesmo padrão visual de `formatCampaignCreatePreview` (`src/cli/mutation-prompt.ts`).
5. O comando exige **confirmação explícita** do operador antes de executar a mutação real (reusar `requireSimpleConfirm` de `src/cli/mutation-prompt.ts`); em `--dry-run`, a confirmação ainda é solicitada mas nenhuma mutação real ocorre (`validate_only: true` na chamada).
6. Se o operador cancelar a confirmação, o comando encerra sem erro (exit 0) e registra a tentativa cancelada no mutation-log (mesmo padrão de `create.ts` — sucesso e cancelamento são ambos auditados).
7. Após criação bem-sucedida (real, não dry-run), o comando registra uma entrada em `appendMutationLog` (`src/log/mutation-log.ts`) com uma nova operação de auditoria dedicada a esta ação (ex.: `create_audience_remarketing`, adicionada ao union type `MutationOperation`).
8. **Tratamento de erro:** se a chamada à API falhar (ex.: permissão negada, conta sem o recurso habilitado, argumento inválido), o comando exibe mensagem PT-BR acionável via `printError`/`errors/error-map.ts` — nunca um stack trace cru. Se o código de erro retornado pela API não estiver mapeado, cai no fallback genérico já existente no error-map (não é necessário mapear um código novo especificamente para audiences nesta story, a menos que a validação real revele um código específico).
9. **Boundary rule respeitada:** toda chamada ao SDK `google-ads-api` para esta feature fica isolada em um módulo dedicado dentro de `src/google-ads-api/` (ex.: `audience.ts`); nenhuma importação de `google-ads-api` fora desse diretório (mesma regra de `client.ts`, `mutations.ts`, `adapter.ts`, `accounts.ts`).
10. Ao concluir com sucesso, a saída mostra o `resource_name` da `user_list` criada e uma seção de "próximos passos" em PT-BR mencionando explicitamente que a lista deve ser **aplicada a uma campanha** para começar a segmentar (referência textual à Story 9.2 — sem implementar a aplicação nesta story).
11. Testes unitários (≥80% cobertura nos arquivos de lógica pura novos):
    - Validador de inputs (nome não vazio/≤255 chars, `membership-days` dentro da faixa aceita) — puro
    - Builder que monta a(s) `MutateOperation<resources.IUserList>` para a regra "todos os visitantes" — puro, mocando apenas o shape de entrada/saída (não a chamada de rede)
    - Formatter do preview — puro
    - Handler do comando com SDK mockado (`getCustomer` retornando um fake com `mutateResources` espionado, mesmo padrão de `src/google-ads-api/mutations-removal.test.ts`), cobrindo: sucesso, cancelamento, dry-run, erro de API

### Completion Notes

**Decisão R3 — `MutationLogEntry.campaignId`:** tornado **opcional** (`campaignId?: string`) em `src/log/mutation-log.ts`, em vez de usar valor sentinela. Justificativa: varredura confirmou que **nenhum consumidor** lê `campaignId` como campo obrigatório (única referência ao tipo fora da definição é um teste que valida campos opcionais; o log é fire-and-forget escrito em `~/.aiox/google-ads-mutations.log`, nunca relido pelo código). Tornar opcional é não-breaking — todos os writers de campanha existentes continuam passando `campaignId` normalmente. Entradas de audience **omitem** o campo (mais limpo que `campaignId: ''`).

**Decisão resource_name em dry-run:** em `validate_only: true` o Google valida a operação mas NÃO cria a lista e NÃO devolve um resource_name real. `createRemarketingUserList` retorna `resourceName: ''` (string vazia) nesse caso, documentado no JSDoc e no tipo `RemarketingUserListResult`. A saída do comando em dry-run não imprime resource_name (apenas "dry-run validado — nenhuma lista foi criada").

**API do SDK escolhida:** `customer.mutateResources([operation], {validate_only, partial_failure:false})` genérico (mesmo shape de `createSearchCampaign`), em vez de `customer.userLists.create(...)`. Motivo: consistência com o padrão já estabelecido no pacote (leitura de `resource_name` via `mutate_operation_responses[0].user_list.resource_name`, mesmo helper `asMutateEntry`) e caminho mais direto para a Story 9.2 encadear o resource_name retornado se necessário.

**Shape do `rule_based_user_list` (R1) — validado, não assumido:** conferido contra `node_modules/google-ads-node/build/protos/protos.d.ts` (v23): `IUserList` (membership_status, membership_life_span, rule_based_user_list), `IRuleBasedUserListInfo` (prepopulation_status, flexible_rule_user_list), `IFlexibleRuleUserListInfo` (inclusive_rule_operator, inclusive_operands), `IFlexibleRuleOperandInfo` (rule), `IUserListRuleInfo` (rule_type, rule_item_groups), `IUserListRuleItemGroupInfo` (rule_items), `IUserListRuleItemInfo` (name, string_rule_item), `IUserListStringRuleItemInfo` (operator, value). Enums usados como **string literal** (convenção de `campaign-builder.ts`): `OPEN`, `REQUESTED`, `AND`, `OR_OF_ANDS`, `CONTAINS` — todos confirmados como chaves válidas dos respectivos enums.

**Boundary rule (AC#9, Artigo VI):** `src/google-ads-api/audience.ts` é o único arquivo novo que importa `google-ads-api` (apenas types + `getCustomer` de `client.ts`). `src/cli/commands/audience.ts` consome só o adapter/validator/types — não importa o SDK.

**Não portado (por design):** `checkSessionLimit`/`addToSessionBudget` (criar lista não gasta dinheiro) e `checkCampaignNameExists` (R5 — não confirmado que a API bloqueia nome duplicado de user_list; se bloquear, cai no tratamento de erro padrão via AC#8).
