## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** uma CLI `google-ads` instalada localmente com autenticação OAuth persistida no Keychain,
**so that** os agentes do squad possam executar leituras e operações em tempo real contra a Google Ads API.

## Context

Esta é a primeira story do épico `epic-5-google-ads-agent`, que entrega o equivalente da `meta-ads-agent` para Google Ads. A arquitetura completa está em `docs/architecture/google-ads-agent.md`. O handoff do @architect para o @dev está em `.aiox/handoffs/handoff-architect-to-dev-google-ads-agent-2026-05-21T13-20.yaml`.

**Por que essa story é a primeira:** sem scaffold + auth, nenhum outro comando pode ser construído (accounts, config, report). Ela estabelece o pacote, a infraestrutura comum (logger, errors, config, keychain) e o fluxo OAuth — fundação para 5.2 e 5.3.

**O que NÃO faz parte desta story:**
- `accounts` (5.2)
- `config set-default` (5.2)
- `report` (5.3)

## Acceptance Criteria

1. Pacote `packages/google-ads-agent/` criado com estrutura espelhando `packages/meta-ads-agent/` (mesmo `tsup.config.ts`, `tsconfig.json`, `eslint.config.js`, layout `src/`, `bin/`)
2. `package.json` declara: `name: "@aiox/google-ads-agent"`, `bin: { "google-ads": "./dist/bin/google-ads.js" }`, scripts `build`/`dev`/`lint`/`test`, dependência `google-ads-api: ^23.0.0` (e demais espelhadas da meta-ads exceto SDK Meta)
3. `node dist/bin/google-ads.js --help` exibe os comandos `auth` (e subcomandos `setup`, `manual`, `status`) — accounts/config/report virão nas próximas stories
4. Módulo `src/auth/keychain.ts` persiste 6 chaves no macOS Keychain sob service name `google-ads-agent`: `developer-token`, `client-id`, `client-secret`, `refresh-token`, `customer-id`, `login-customer-id`
5. Comando `google-ads auth setup` executa fluxo OAuth interativo: prompts dev-token + client_id/secret → abre URL de autorização Google → recebe code via loopback `http://localhost:8765/oauth/callback` (porta configurável via `GOOGLE_ADS_OAUTH_PORT`) → troca por refresh_token → persiste no Keychain
6. Comando `google-ads auth manual` aceita paste manual de `client_id|client_secret|refresh_token|developer_token` (fallback quando OAuth loopback bloqueado por firewall)
7. Comando `google-ads auth status` chama `client.listAccessibleCustomers(refreshToken)` da SDK e retorna verde (✓) com lista de IDs acessíveis se válido, ou vermelho (✗) com mensagem PT-BR acionável apontando para `auth setup` se qualquer chave faltar/inválida
8. Mensagens de erro centralizadas em `src/errors/` traduzidas para português (mínimo: `UNAUTHENTICATED`, `PERMISSION_DENIED`, `INVALID_ARGUMENT`, `UNAVAILABLE`, `DEADLINE_EXCEEDED`, network errors `ENOTFOUND`/`ETIMEDOUT`/`ECONNREFUSED`)
9. Boundary rule respeitada: apenas arquivos em `src/google-ads-api/` importam o pacote npm `google-ads-api`; demais módulos consomem somente as funções do adapter port (a Story 5.1 cria o `client.ts` mínimo necessário para auth; o `adapter.ts` para reports fica para 5.3)
10. Logger em `src/cli/logger.ts` ativo via `GOOGLE_ADS_DEBUG=1` (pino + pino-pretty em dev, pino puro em prod), idêntico ao pattern meta-ads
11. Testes unitários (vitest) cobrindo: `keychain` (mock keytar), `error-map` (top 6 códigos), `oauth-flow` URL builder (sem hit de rede), com mínimo 80% de cobertura nos arquivos novos
12. `npm run lint` clean, `npm run build` produz `dist/bin/google-ads.js`, smoke manual: `auth setup` end-to-end com conta Google Ads real escreve as 5 chaves no Keychain (login-customer-id opcional)

### Differences from Meta

| Aspecto | Meta | Google |
|---------|------|--------|
| Service name (keychain) | `meta-ads-agent` | `google-ads-agent` |
| Env debug var | `META_ADS_DEBUG` | `GOOGLE_ADS_DEBUG` |
| OAuth scope | `ads_management,ads_read,...` | `https://www.googleapis.com/auth/adwords` |
| Token endpoint | `https://graph.facebook.com/v22.0/oauth/access_token` | `https://oauth2.googleapis.com/token` |
| Auth URL | `https://www.facebook.com/v22.0/dialog/oauth` | `https://accounts.google.com/o/oauth2/v2/auth` |
| Token lifetime | 60 dias (access) | refresh_token longo + access_token 1h (SDK renova) |
| Auth keys | 4 (access-token, app-secret, app-id, expiry) | 6 (dev-token, client-id, client-secret, refresh-token, customer-id, login-customer-id) |
| Need dev-token? | No | YES (required header em toda chamada) |
