## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** os comandos `google-ads upload image`, `google-ads upload video`, `google-ads upload text` e `google-ads list-assets` para subir assets (imagens, vídeos referenciados do YouTube e textos curtos) à conta Google Ads,
**so that** eu possa preparar a biblioteca de assets que será consumida pelas RDAs (Story 6.5) e PMax asset_groups (Story 6.3c) sem precisar fazer upload manual pelo UI do Google Ads — com validações client-side que previnem upload de arquivos inválidos.

## Context

Story do **Tier 3 — Mídia e Tipos Avançados** do Epic 6 (`docs/stories/epics/epic-6-google-ads-mutations/EPIC.md`). Stories 6.1, 6.2, 6.3a/b/c, 6.4 entregaram CRUD de campanhas + ad_groups + keywords; Story 6.5 entregou criação de RSA (Search) e RDA (Display).

**Por que essa story precede o uso em escala de RDAs:**
- **Pre-requisite real:** RDAs e PMax asset_groups exigem `Asset.resource_name` como input — sem upload de assets, esses recursos ficam vazios ou caem em assets default do Google
- **Replicação multi-conta:** gestor da MCC Solaro precisa subir o mesmo conjunto de logos/imagens em 24 contas — fazer pelo UI é manual e propenso a erros
- **Biblioteca compartilhada:** assets uma vez criados podem ser referenciados por múltiplos ads → reduz duplicação e custo de gestão

**Decisão arquitetural — escopo do "upload":**

Google Ads tem múltiplos tipos de asset com semânticas distintas:

| Tipo | O que é | Esta story |
|------|---------|-----------|
| **IMAGE** | Arquivo binário (PNG/JPEG) enviado em base64 | ✅ Sim |
| **LOGO_IMAGE** | Variante de IMAGE com ratios específicos (1:1 ou 4:1) | ✅ Sim |
| **YOUTUBE_VIDEO** | Referência por ID a vídeo público já no YouTube (NÃO sobe arquivo) | ✅ Sim |
| **TEXT** | Snippet de texto reutilizável (headline, descrição) | ✅ Sim |
| **CALL_TO_ACTION_TEXT** | CTA snippet | ❌ POST-MVP |
| **MEDIA_BUNDLE** | HTML5 bundle | ❌ POST-MVP |

**Decisões já confirmadas:**

**O que NÃO faz parte desta story:**

- Delete de assets (Google API não permite delete — apenas órfão até auto-cleanup)

### Magic bytes — image type detection (sem libs externas)

```ts
// PNG signature: 0x89 0x50 0x4E 0x47 0x0D 0x0A 0x1A 0x0A
const PNG_MAGIC = Buffer.from([0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a]);
// JPEG signature: 0xFF 0xD8 0xFF
const JPEG_MAGIC = Buffer.from([0xff, 0xd8, 0xff]);

function detectImageMime(buf: Buffer): 'IMAGE_PNG' | 'IMAGE_JPEG' | null {
  if (buf.length < 8) return null;
  if (buf.subarray(0, 8).equals(PNG_MAGIC)) return 'IMAGE_PNG';
  if (buf.subarray(0, 3).equals(JPEG_MAGIC)) return 'IMAGE_JPEG';
  return null;
}
```

### Dimension extraction sem libs externas

**PNG:** IHDR chunk começa no byte 16. Width = bytes 16-19 (big-endian uint32). Height = bytes 20-23.

**JPEG:** mais complexo — precisa scan dos markers até encontrar SOF0 (0xFFC0) ou SOF2 (0xFFC2). Height = 2 bytes depois do marker length; Width = 2 bytes depois disso.

Implementação manual ~30 linhas. Alternativa: lib `image-size` (~5KB) — aceitável se preferir simplicidade. Decisão @dev.

### YouTube URL parsing — formatos suportados

| Input | video_id |
|-------|----------|
| `https://www.youtube.com/watch?v=dQw4w9WgXcQ` | `dQw4w9WgXcQ` |
| `https://youtu.be/dQw4w9WgXcQ` | `dQw4w9WgXcQ` |
| `https://www.youtube.com/embed/dQw4w9WgXcQ` | `dQw4w9WgXcQ` |
| `https://www.youtube.com/watch?v=dQw4w9WgXcQ&list=...` | `dQw4w9WgXcQ` |
| `dQw4w9WgXcQ` (ID puro) | `dQw4w9WgXcQ` |

YouTube video IDs são sempre 11 chars `[A-Za-z0-9_-]`. Regex: `/[A-Za-z0-9_-]{11}/`.

### Limitação: Assets são create-only (não delete, não edit)

Google Ads API trata assets como **immutable** após criação:
- Não há endpoint `assets.delete`
- Edit = criar novo asset com nome similar (não atualiza in-place)
- Órfãos (assets não referenciados por nenhum ad) são auto-limpos pelo Google após período não-documentado (~30-90 dias na prática)

**Implicação operacional:** Operador deve tratar assets como "append-only" — preferir nomes descritivos com versão (`hero-product-v2-1200x628`) a substituir.

`mutation-log.ts` (Story 6.1) já suporta `MutationLogEntry` genérica. Esta story apenas adiciona 3 novos valores no enum `operation`:
- `'upload_asset_image'`

`before` = `null` (assets são create-only); `after` = `{resourceName, assetId, type, name, ...metadata}`.

## Dev Agent Record

### Execution mode
Auto-story YOLO. Story de média complexidade — file IO + binary parsing sem dependências externas.

### Decisões técnicas

1. **Magic bytes sem libs externas** — PNG (\x89PNG\r\n\x1a\n) + JPEG (\xFF\xD8\xFF). 100% Node.js stdlib.

2. **Parser de dimensões nativo:**
   - **PNG:** IHDR chunk no offset 16 (8 sig + 8 chunk header), width+height são UInt32BE em sequência
   - **JPEG:** Walk de markers buscando SOF0 (0xFFC0-0xFFCF excluding 0xC4/C8/CC); dimensions em UInt16BE

3. **`validateLogoDimensions` com tolerância ±10%** — Google aceita ratios fora do exato 1:1 ou 4:1, então damos slack. `isRecommended` indica qualidade.

4. **`parseYoutubeUrl` aceita 4 formatos** — youtube.com/watch?v=, youtu.be/, embed/, raw 11-char ID. Regex matching simples sem URL parsing pesado.

5. **Hidden file edge case** — `.png` (arquivo só com extensão) → basename retorna `.png` (não strip ext). Tratado: se startsWith `.`, faz slice(1). Documentado em test.

6. **Asset upload via base64** — image bytes convertidos com `buffer.toString('base64')` antes de enviar no mutate. Conforme SDK Opteo + Google API spec.
