## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** o comando `google-ads update budget` e `google-ads update bidding` que ajustam orçamento diário e estratégia de lance de campanhas existentes via CLI,
**so that** eu possa fazer a operação mais frequente do dia-a-dia (ajustes de budget e lance) sem abrir o Google Ads UI — com veto conditions específicas que previnem aumento acidental >50% e protegem contra runaway-spend.

## Context

Primeira story do **Epic 6 — Google Ads CLI Mutations** (`docs/stories/epics/epic-6-google-ads-mutations/EPIC.md`). Stories 5.1-5.4 do Epic 5 entregaram o MVP de **read + coordenação manual**. Esta story inicia as **mutações reais via CLI**.

**Por que essa é a primeira mutação:**
- **Frequência:** gestor ajusta budget/lance 50x para cada campanha que cria
- **Risco controlável:** budget update é reversível (basta voltar ao valor anterior); pause/enable também
- **Validação do pipeline:** confirma que adapter port suporta `customer.mutate(...)` antes de partir para create (mais complexo)

**Decisão arquitetural (re-priorização vs sugestão inicial):**
O @qa originalmente sugeriu começar por `campaign create`. Após análise, o @pm e o usuário concordaram em começar por **update budget/bidding** porque o gestor da MCC Solaro já tem 24 contas com campanhas existentes — atualizar orçamento entrega valor IMEDIATO, enquanto create só vale para campanhas novas.

**Sandbox confirmado:** customer-id `5562216599` ("Solaro Marketing e Vendas" — sub-conta da MCC, ENABLED, em BRL). Token Standard Access — todas as mutações autorizadas.

**O que NÃO faz parte desta story:**
- Criar campanhas (Story 6.3a/6.3b/6.3c)
- Pausar / reativar (Story 6.2)
- Alterar audiences, keywords, ads (Stories 6.4/6.5)
- Mudanças em conversion tracking (out of epic)
- Budget de ad_group (apenas campaign-level nesta story)

## Risks

| ID | Risco | Probabilidade | Impacto | Mitigação |
|----|-------|--------------|---------|-----------|
| R1 | **Runaway spend** — operator aumenta budget 10x acidentalmente | Média | **Crítico financeiro** | Threshold +50% default exige double-confirm; output mostra valor antigo + novo + delta % antes da confirmação |
| R2 | Mudança de bidding strategy quebra performance da campanha | Média | Alto | Warning explícito quando muda de Maximize Conversions → Manual CPC (ou inverso); cita janela de aprendizado de ~14 dias |
| R3 | Propagação ~30min do Google após mutação | Alta | Baixo | Aceito — operação assíncrona; report subsequente pode mostrar "stale" temporariamente; documentar |
| R4 | Concurrent edit (operator no UI + CLI) | Baixa | Médio | Pre-fetch + diff: se valor atual diverge do esperado pelo operator, pausa e mostra diff |
| R5 | Mutate exige `validate_only=true` primeiro? | Baixa | Baixo | SDK Opteo aceita ambos; usar `validate_only` em `--dry-run` (não default) |
| R6 | Standard Access ainda tem rate limits granulares | Baixa | Baixo | 15k/dia é folga grande; nenhum problema esperado |

## Acceptance Criteria

1. Novo subcomando `google-ads update` registrado no CLI (parent de operações de mutação)
2. Subcomando `google-ads update budget <campaign-id>` aceita:
   - `--daily <amount>` (R$ ou USD, depende da conta) — novo valor de budget diário
   - `--customer-id <id>` (opcional — usa default)
   - `--dry-run` (validate_only=true; não aplica mudança real)
   - `--max-budget-increase <pct>` (default 50; configurável por sessão)
3. Subcomando `google-ads update bidding <campaign-id>` aceita:
   - `--strategy <maximize_conversions|target_cpa|target_roas|manual_cpc|maximize_conversion_value>`
   - `--target <value>` (CPA em currency ou ROAS como decimal, dependendo de strategy)
   - `--customer-id <id>`, `--dry-run`
4. Pre-fetch obrigatório: antes de aplicar, CLI faz `customer.query` para ler:
   - Budget atual (em micros)
   - Bidding strategy atual + target
   - Status da campanha (ENABLED/PAUSED/REMOVED)
   - Nome da campanha (para confirmação ao operator)
5. Anti-runaway-spend (Veto crítico):
   - Se `novo_budget > budget_atual * (1 + max_budget_increase/100)`: pausa, mostra delta %, exige double-confirm explícito ("sim, aumentar de X para Y" — não basta Enter)
   - Se `novo_budget < budget_atual * 0.1`: warning "redução >90%" (não bloqueia, mas alerta)
6. Confirmation UX antes de mutar:
   ```
   📋 Mudança proposta — Campanha {name} ({campaign-id})
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Budget atual:     R$ 30,00/dia
   Budget novo:      R$ 60,00/dia (+100% — ACIMA DO LIMITE 50%)
   Strategy atual:   Maximize Conversions
   Strategy nova:    (sem mudança)
   Conta:            5562216599 (Solaro Marketing e Vendas)
   ⚠️ Aumento de +100% excede limite anti-runaway (50%).
   Confirme digitando "sim, aumentar de R$ 30 para R$ 60":
   ```
7. Veto: se campanha está `REMOVED` (deletada), comando exit 1 com mensagem PT-BR; não tenta mutar
8. Veto: se customer-id não bater ou for MCC, exit 1 com mensagem orientativa (Story 5.4 já bloqueia, mas explícito aqui também)
9. Output pós-mutate: mostra `resource_name` retornado pela API + link direto ao Google Ads UI para verificação
10. Log local de mutação em `~/.aiox/google-ads-mutations.log` (JSON Lines): timestamp, customer_id, campaign_id, operation, before_value, after_value, dry_run flag — para auditoria e rollback manual
11. Boundary rule respeitada — toda lógica de SDK mutate fica em `src/google-ads-api/mutations.ts` (novo arquivo dentro do adapter port)
12. Testes unitários (≥80% cobertura nos arquivos novos):
    - `calculateBudgetDelta(old, new): {pct, exceeds_threshold}` (puro)
    - `formatMutationDiff(before, after): string` (puro — UX)
    - `parseMicros(value: string): number` (converter R$ 30,00 → 30_000_000)
    - `appendMutationLog(...)` com mock fs
13. Smoke real-time: contra customer `5562216599`:
    - Pegar 1 campanha existente (qualquer)
    - `update budget --daily 1 --dry-run` (validate_only — não muta)
    - Verificar que CLI mostra preview correto
    - Tentar `update budget --daily {atual * 2.5}` (gatilho anti-runaway 150%)
    - Verificar que CLI pede double-confirm e bloqueia se não confirmar
    - `update budget --daily {atual * 1.1}` (10% — dentro do limite)
    - Aplicar real, verificar via `report` que o novo budget propagou (após ~30min OU verificar via `customer.query` direto que retorna o novo valor mais rápido)

### SDK signature — mutateResources

```ts
import { GoogleAdsApi } from 'google-ads-api';

const customer = client.Customer({ customer_id, refresh_token, login_customer_id });

// Update budget — campanha referencia campaign_budget; mutamos o budget resource
const result = await customer.mutateResources([
  {
    entity: 'campaign_budget',
    resource_name: `customers/${customer_id}/campaignBudgets/{budget_id}`,
    operation: 'update',
    update_mask: { paths: ['amount_micros'] },
    amount_micros: newAmountMicros,
  },
], {
  validate_only: dryRun, // true para --dry-run
});

// result.results contém os resource_names atualizados
```

Para descobrir o `campaign_budget` resource_name de uma campaign:

```sql
SELECT
  campaign.id,
  campaign.name,
  campaign.status,
  campaign_budget.amount_micros,
  campaign_budget.resource_name
FROM campaign
WHERE campaign.id = {campaign_id}
```

### Conversão de currency

Google Ads sempre usa **micros** (1 unit = 1_000_000 micros). Parser deve aceitar "R$ 30", "30", "30.00", "30,00" e converter para `30_000_000`. Formatter inverso para output.

### Veto Conditions (não fazer)

- ❌ Aplicar mutate sem pre-fetch (precisa do valor atual para diff)
- ❌ Aceitar "sim" simples quando double-confirm é exigido (frase exata)
- ❌ Não logar mutação aplicada (auditoria é parte do AC#10)
- ❌ Logar tokens / refresh_token no mutation log (apenas IDs + valores numéricos)
- ❌ Importar `google-ads-api` (npm) fora de `src/google-ads-api/`

## Dev Agent Record

### Execution mode
Interactive (conforme recomendação @po). Pontos de checkpoint humano (todos passaram limpo):

1. **SDK research:** confirmado shape `MutateOperation<T>` + `mutateResources(operations, options)` com `validate_only: true` para dry-run
2. **Visual do double-confirm UX:** validado no smoke 1 (cancelou corretamente quando stdin não respondeu)
3. **Fallback validate_only:** API aceita em ambas operações (budget + bidding) — sem necessidade de fallback

### Decisões técnicas tomadas

1. **Mutate campaign_budget direto (não Campaign):** Google separa budget como entity própria; `update_mask: { paths: ['amount_micros'] }` apenas no budget resource. Mais limpo que tentar mutar `campaign.daily_budget_micros` (que não existe).

2. **Pre-fetch obrigatório antes do mutate:** sem isso, não há diff para mostrar ao operator. Custo ~1 query GAQL adicional por mutate — aceito para audit + UX.

3. **`parseMicros` com auto-detect BR vs US separators:** se tem `,` depois do `.`, comma é decimal (BR style); caso contrário comma é separador de milhares. Cobre 99% dos casos.

4. **`requireDoubleConfirm` case-insensitive + trim:** mais ergonômico que match exato. Mas exige a FRASE INTEIRA — não basta "sim".

5. **`--login-customer-id` flag aditiva:** descoberto durante smoke que report/update sem essa flag falham para contas-cliente. Adicionada como flag opcional em update (não mexi no report — Story 5.3 mantém). Solução não-quebrante.

6. **Strategy-specific fields mutuamente exclusivos:** Google rejeita se target_cpa e manual_cpc são preenchidos juntos. Code constrói update_mask paths dinamicamente baseado na strategy escolhida.

7. **Sort de tree nodes (Story 5.4) preservado:** parseCustomerClientRow + sort estável continuam funcionando — sem regressão.
