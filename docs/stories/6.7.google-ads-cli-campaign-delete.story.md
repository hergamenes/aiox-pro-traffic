## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** o comando `google-ads remove campaign <campaign-id>` (e `remove ad-group`) que marca campanhas/ad_groups como `REMOVED` na API do Google via CLI — com **triple-confirm**, `--dry-run` ligado por default e pre-fetch obrigatório de gasto recente,
**so that** eu possa fazer limpeza segura de campanhas obsoletas **sem acidente irreversível** — sabendo que `REMOVED` no Google Ads é uma operação **definitiva sem API de restore** e que esse é o último resort após considerar pausar (`PAUSE`).

## Context

**Última story do Epic 6 — Google Ads CLI Mutations** (`docs/stories/epics/epic-6-google-ads-mutations/EPIC.md`). Encerra o épico cobrindo a operação **mais destrutiva** do ciclo: remoção.

**Por que essa é a story de maior risco do épico (Tier 4):**

| Aspecto | Realidade do Google Ads |
|---------|-------------------------|
| "Delete" no Google Ads | **Não existe** — só existe `status = REMOVED` (soft-delete) |
| Restore via API | **Não existe** — uma vez `REMOVED`, fica `REMOVED` para sempre |
| Cascade | Remover campanha **remove silenciosamente todos os ad_groups e ads filhos** |
| Visibilidade pós-remove | Query padrão `WHERE campaign.status IN (ENABLED, PAUSED)` **não retorna** campanhas removidas — operador "perde" a campanha na UI |
| Dados históricos | **Permanecem** para relatórios; spend acumulado continua nos totais |
| Diferença vs `PAUSE` | `PAUSE` é reversível (pode voltar a `ENABLED`); `REMOVED` **não é** |

**Por que essa story chega por último no Epic 6:**
- Operações reversíveis (budget/bidding/pause/create) já estão estabilizadas — operador tem ferramentas seguras antes de ganhar a destrutiva
- Padrões de pre-fetch + confirmação dupla + audit log já validados pelas stories 6.1-6.6
- Esta story **endurece** esses padrões: pre-fetch é obrigatório (não opcional), `--dry-run` é **default** (não opt-in), confirmação é **tripla**

**Sandbox confirmado:** customer-id `5562216599` ("Solaro Marketing e Vendas"). Token Standard Access — autorização para mutate `remove` confirmada.

**O que NÃO faz parte desta story:**
- Restore / undelete (não existe API)
- Remoção em lote / `--all` (proibido explicitamente — uma campanha por invocação)
- Remoção de keywords / ads individuais (escopo do Story 6.4/6.5 se necessário no futuro)
- Limpeza de campaign_budgets órfãos (Google gerencia GC automaticamente)
- Remoção via squad agent autônomo (`*remove` no campaign-optimizer ficaria atrás de flag manual extra; out of scope)

## Risks

| ID | Risco | Probabilidade | Impacto | Mitigação |
|----|-------|--------------|---------|-----------|
| R1 | **Remoção IRREVERSÍVEL** — operador remove campanha errada e não há undo via API | Média | **Crítico** | `--dry-run` é DEFAULT; só executa real com `--confirm-delete`; triple-confirm exige digitar nome COMPLETO da campanha; warning explícito "IRREVERSÍVEL — não há API de restore" no prompt |
| R2 | **Cascade silencioso** — remover campanha apaga todos ad_groups e ads filhos sem alertar | Alta | **Crítico** | Pre-fetch obrigatório lista counts (`N ad_groups`, `M ads`); UX mostra "Esta ação removerá também: N ad_groups, M ads" antes do confirm |
| R3 | **Confusão "onde foi a campanha?"** — dados preservados em relatórios mas campanha some das queries padrão | Alta | Médio | Output pós-remove instrui: "campanha agora invisível em queries default; use `WHERE status IN (ENABLED, PAUSED, REMOVED)` para localizar"; cita link UI com filtro `removed` |
| R4 | **Operador confunde REMOVE com PAUSE** — usa REMOVE quando PAUSE era suficiente | Alta | **Crítico** | Prompt inicial SEMPRE sugere PAUSE como alternativa: "Se você precisa só PARAR a campanha, use `google-ads pause` (reversível); use REMOVE apenas se quiser limpar definitivamente"; quebra de fluxo intencional |
| R5 | **Race com UI** — operador no Google Ads UI muda status enquanto CLI tenta remover | Baixa | Médio | Pre-fetch lê status atual; se campanha já é `REMOVED`, comando é idempotente (no-op + warning); se status mudou entre pre-fetch e mutate, API retorna erro e CLI exibe diff |
| R6 | **Gasto recente** — operador remove campanha que ainda gastou nas últimas 24h (provavelmente em uso) | Média | Alto | Pre-fetch lê spend em 24h/7d/90d; se spend_24h > 0, exige TRIPLE-confirm extra: "sim, remover campanha com gasto recente" (frase fixa, case-insensitive) |
| R7 | **Tentação de batch** — operador quer remover 10 campanhas e tenta `--all` ou shell loop | Baixa | Alto | CLI rejeita `--all`, `--batch`, qualquer flag de massa; hard cap de 1 remove por invocação; documentação explícita: "não scripte loops sobre este comando" |
| R8 | **MCC remove sub-conta** — operador passa MCC id por engano | Baixa | **Crítico** | Boundary herdada da Story 5.4: comando rejeita se customer é MCC; mensagem orientativa em PT-BR |

## Acceptance Criteria

1. Novo subcomando `google-ads remove` registrado no CLI (parent de operações destrutivas)
2. Subcomando `google-ads remove campaign <campaign-id>` aceita:
   - `--customer-id <id>` (opcional — usa default)
   - `--login-customer-id <id>` (opcional, para acessar sub-contas MCC)
   - `--confirm-delete` (flag explícita; **sem essa flag, comando SEMPRE roda dry-run**)
   - **NÃO aceita** `--all`, `--batch`, `--from-file` ou qualquer flag de massa (CLI rejeita com erro orientativo)
3. Subcomando `google-ads remove ad-group <ad-group-id>` aceita o mesmo conjunto de flags (mesmo padrão UX)

## Dev Notes

### Por que `--dry-run` é DEFAULT (e não opt-in como nas outras stories do épico)

Nas stories 6.1-6.6, `--dry-run` é opt-in: você passa a flag quando quer simular. O default é aplicar.

Story 6.7 inverte: `--dry-run` é o **modo default implícito**. O operador precisa passar `--confirm-delete` para sair desse modo. Razão: a operação é **irreversível** e a fricção extra (uma flag adicional) é desejável.

```
6.1-6.6:  google-ads update budget ... --daily 50           # APLICA real
6.1-6.6:  google-ads update budget ... --daily 50 --dry-run # SIMULA

6.7:      google-ads remove campaign 123                    # SIMULA (default)
6.7:      google-ads remove campaign 123 --confirm-delete   # APLICA real
```

Essa inversão é intencional e deve ser destacada em `--help` do comando.

### Por que sempre sugerir PAUSE primeiro

`PAUSE` é a operação que 90% dos casos resolvem o que o operador "achou que precisava remover". Exemplos típicos:
- "Vou tirar essa campanha do ar por enquanto" → **PAUSE** (reativável depois)
- "Vou economizar verba esse mês" → **PAUSE**
- "Vou trocar de criativo" → **PAUSE** + edita ads
- "Vou desligar definitivamente esse cliente" → **REMOVE** (raro)

A primeira tela do confirm força o operador a passar mentalmente por essa pergunta. Custo de fricção é baixo (1 tecla "s/N"); benefício é alto (evita acidentes do tipo "achei que PAUSE não existia").

### Audit log como única "recuperação" forense

Após REMOVE, a única forma de saber "o que havia ali" é o audit log local. Por isso o snapshot `before` é deliberadamente verboso:
- Nome da campanha (para identificar)
- Budget + bidding (para recriar se necessário)
- Spend em 3 janelas (para entender se estava ativa)
- Counts de ad_groups e ads (para dimensionar a recriação)

`operator_confirmed_phrase` é registrado para forense: se houver disputa ("eu não autorizei isso"), o log mostra exatamente o que foi digitado.

### SDK signature — remove

```ts
import { GoogleAdsApi, MutateOperation, resources } from 'google-ads-api';

const customer = client.Customer({ customer_id, refresh_token, login_customer_id });

const operations: MutateOperation<resources.ICampaign>[] = [
  {
    entity: 'campaign',
    operation: 'remove',
    resource_name: `customers/${customer_id}/campaigns/${campaign_id}`,
    // NO update_mask — remove não tem fields para mascarar
  },
];

const result = await customer.mutateResources(operations, { validate_only: dryRun });
// result.results[0].resource_name retorna o resource removido (mesmo em dry-run via validate_only)
```

**Detalhe SDK:** `operation: 'remove'` (não `'delete'` — a terminologia do Google é "remove" porque é soft-delete). Não há método `customer.delete(...)` — sempre via `mutateResources`.

### Pre-fetch GAQL composta

```sql
-- Query 1: campanha + budget + bidding + status
SELECT
  campaign.id,
  campaign.name,
  campaign.status,
  campaign_budget.amount_micros,
  campaign.bidding_strategy_type
FROM campaign
WHERE campaign.id = {campaign_id}

-- Query 2: counts (uma query única agregada se SDK suportar; senão 2 queries simples)
```
