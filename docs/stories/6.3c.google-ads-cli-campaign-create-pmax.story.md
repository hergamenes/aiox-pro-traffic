## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** o comando `google-ads create campaign-pmax` que cria campanhas Performance Max (PMax) via CLI — com `asset_group` skeleton e bidding orientado a conversão,
**so that** eu possa publicar campanhas PMax (o tipo mais complexo e com maior potencial de escala via AI do Google) sem abrir o UI, mantendo as veto conditions de orçamento e adicionando os pre-flight checks específicos de PMax (conversion_action obrigatório, final_url obrigatório, asset_group skeleton criado atomicamente).

## Context

Terceira story do bloco de criação do **Epic 6 — Google Ads CLI Mutations** (`docs/stories/epics/epic-6-google-ads-mutations/EPIC.md`), dentro do split da 6.3 em três sub-stories por tipo de campanha (6.3a Search, 6.3b Display, 6.3c PMax).

**Por que PMax é separado e maior (8 pts H):**
- **PMax não usa `ad_group` tradicional** — usa `asset_group`, uma entidade nova ainda não tocada nas 6.3a/6.3b
- **Bidding obrigatoriamente orientado a conversão** — `target_roas` (com `conversion_value` configurado) ou `maximize_conversion_value`; não aceita Manual CPC nem Maximize Clicks
- **Pre-requisito Google:** conta precisa ter pelo menos uma `conversion_action` em status `ENABLED` — sem isso PMax não roda (mesmo PAUSED ele recusa)
- **Asset Group exige assets mínimos para servir** — mas a entidade `asset_group` pode ser criada VAZIA (PAUSED), com os assets sendo anexados posteriormente. Esta story entrega o **skeleton multi-entity atômico** (CampaignBudget + Campaign + AssetGroup), e o anexar de assets reais (logos, imagens, headlines, descriptions, business name, videos) é trabalho da Story 6.6
- **Auditoria mais complexa:** mutate atômico com 3 entidades retorna 3 `resource_names`; log precisa registrar os 3 com referências cruzadas para permitir rollback manual

**Sandbox confirmado:** customer-id `5562216599` ("Solaro Marketing e Vendas" — sub-conta da MCC, ENABLED, em BRL). Token Standard Access. Para esta story precisamos validar via GAQL que existe pelo menos 1 `conversion_action` ENABLED no sandbox antes do smoke real — se não houver, o smoke documenta skip do passo de criação real e roda apenas `--dry-run`.

**Reuso das 6.3a/6.3b:**
- `parseMicros` / `formatMicros` / anti-runaway threshold de orçamento — herdados (não duplicar)
- `requireDoubleConfirm` para o aumento de budget contra `--max-session-budget` — herdado
- MCC veto / customer-id veto / dry-run pattern — herdados
- `appendMutationLog` — extendido com `operation: 'create_campaign_pmax'`
- `createSearchCampaign` (6.3a) e `createDisplayCampaign` (6.3b) servem de **template arquitetural** — mas PMax tem campos exclusivos (`maximize_conversion_value`, `asset_group`, `final_url_expansion`)

**O que NÃO faz parte desta story:**
- Anexar assets reais (logos, imagens, headlines, descriptions, videos) ao asset_group — fica para Story 6.6
- `Listing groups` (retail/shopping com feed de produtos) — POST-MVP, fora do epic
- Editar campanha PMax existente (mexer em ROAS target, etc.) — esperar Story 6.4 ou nova story dedicada
- Mexer em conversion_action (criar, editar) — out of epic
- Mexer em audience signals — POST-MVP

**Justificativa:** PMax é, de longe, o tipo de campanha mais complexo do Google Ads. Esta story introduz uma entidade NOVA no codebase (`asset_group`), exige mutate atômico de 3 entidades com `resource_name` placeholders negativos (`-1`, `-2`, `-3`), bidding obrigatoriamente orientado a conversão, pre-flight check de `conversion_action` no GAQL, e auditoria multi-resource. Dobrou o ponto da 6.3a/6.3b (5→8) por causa do skeleton multi-entity + pre-flight extra + risco operacional de rodar PMax sem assets (não serve impressões, mas a entidade pode ser criada).

## Dev Notes

### SDK signature — mutateResources atômico de 3 entidades

```ts
import { GoogleAdsApi, resources, enums, MutateOperation } from 'google-ads-api';

const customer = client.Customer({ customer_id, refresh_token, login_customer_id });

// Placeholders negativos: -1, -2, -3 — Google substitui pelos IDs reais e resolve referências cruzadas
const operations: MutateOperation<
  resources.ICampaignBudget | resources.ICampaign | resources.IAssetGroup
>[] = [
  {
    entity: 'campaign_budget',
    operation: 'create',
    resource: {
      resource_name: `customers/${customer_id}/campaignBudgets/-1`,
      name: `${name} - Budget`,
      amount_micros: dailyMicros,
      delivery_method: enums.BudgetDeliveryMethod.STANDARD,
    },
  },
  {
    entity: 'campaign',
    operation: 'create',
    resource: {
      resource_name: `customers/${customer_id}/campaigns/-2`,
      name,
      advertising_channel_type: enums.AdvertisingChannelType.PERFORMANCE_MAX,
      status: enums.CampaignStatus.PAUSED,
      campaign_budget: `customers/${customer_id}/campaignBudgets/-1`,
      start_date: formatGoogleDate(startDate),
      ...(endDate ? { end_date: formatGoogleDate(endDate) } : {}),
      ...(biddingStrategy === 'target_roas'
        ? { maximize_conversion_value: { target_roas: targetRoas } }
        : { maximize_conversion_value: {} }),
      url_expansion_opt_out: false,
    },
  },
  {
    entity: 'asset_group',
    operation: 'create',
    resource: {
      resource_name: `customers/${customer_id}/assetGroups/-3`,
      name: `${name} - Asset Group 1`,
      campaign: `customers/${customer_id}/campaigns/-2`,
      final_urls: [finalUrl],
      status: enums.AssetGroupStatus.PAUSED,
    },
  },
];

const result = await customer.mutateResources(operations, {
  validate_only: dryRun,
});

// result.mutate_operation_responses preserva a ordem dos operations.
// Index 0 → budget, 1 → campaign, 2 → asset_group
```

### Por que `asset_group` skeleton aqui e não em 6.6

Decisão arquitetural: cada Campaign PMax precisa de pelo menos 1 AssetGroup ligado para ser "complete" semanticamente. Mas a entidade pode ser criada VAZIA (sem assets anexados) e em status PAUSED. Story 6.6 entrega o anexar de assets (logos 3+, imagens 3+, headlines 5+, long headline 1+, descriptions 4+, business name 1+, videos opcionais).

Esta divisão isola riscos:
- 6.3c valida o pipeline mutate atômico 3-entidades (alta complexidade arquitetural)
- 6.6 valida o pipeline de upload + asset_group_asset linking (alta complexidade de media/binary handling)

### Pre-flight check de `conversion_action` — GAQL exato

```sql
SELECT
  conversion_action.id,
  conversion_action.name,
  conversion_action.status,
  conversion_action.value_settings.default_value
FROM conversion_action
WHERE conversion_action.status = 'ENABLED'
```

- Se 0 retornos → veto AC#4 (PMax recusa rodar; melhor falhar cedo no CLI que esperar erro Google opaco)
- Se ≥1 retorno e `value_settings.default_value > 0` → ok para `target_roas` ou `maximize_conversion_value`
- Se ≥1 retorno mas todos `value` = 0 → warning AC#3 quando strategy=`target_roas`

### Rationale do `--max-session-budget` em PMax

Mesmo herdado de 6.3a/b, vale reforçar: PMax tem learning phase 7-14 dias durante o qual o Google "explora" agressivamente. Operator que cria PMax sem entender pode queimar budget rápido. Default `--max-session-budget` de R$ 1000/mês (≈R$ 33/dia) é razoável para campanha de aprendizado; double-confirm acima disso.

### Rollback manual — ordem importante

Se precisar deletar uma campanha PMax criada por esta story (ex: smoke deu errado):

```
1. Delete AssetGroup (resource_name registrado no log)
2. Delete Campaign (resource_name registrado no log)
3. Delete CampaignBudget (se não compartilhado com outras campaigns)
```

Story 6.7 fará isso automaticamente com `--cascade-pmax`. Por ora, audit log de 6.3c registra os 3 resource_names ordenados.

### Veto Conditions (não fazer)

- ❌ Criar campanha PMax com status diferente de PAUSED
- ❌ Aceitar bidding strategy fora de `maximize_conversion_value` ou `target_roas`
- ❌ Criar sem `final_url` (PMax exige obrigatório)
- ❌ Criar sem conversion_action ENABLED no account
- ❌ Anexar assets nesta story (escopo da 6.6)
- ❌ Importar `google-ads-api` (npm) fora de `src/google-ads-api/`
- ❌ Logar tokens / refresh_token no mutation log
