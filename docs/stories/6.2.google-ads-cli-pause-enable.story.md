## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** os comandos `google-ads pause` e `google-ads enable` que alternam o status de campanhas e ad_groups entre `ENABLED ↔ PAUSED` via CLI,
**so that** eu possa pausar e reativar campanhas/ad_groups em segundos (operação reversível) sem abrir o Google Ads UI — com pre-fetch, veto contra entidades `REMOVED` e audit log completo para rollback.

## Context

Segunda story do **Epic 6 — Google Ads CLI Mutations** (`docs/stories/epics/epic-6-google-ads-mutations/EPIC.md`). Story 6.1 (`update budget` + `update bidding`) entregou o **primeiro pipeline de mutação real** com adapter port (`mutations.ts`), audit log (`~/.aiox/google-ads-mutations.log`) e veto conditions com double-confirm. Esta story **reusa o pipeline** e adiciona a operação mais segura e mais frequente após budget: pausar/reativar.

**Por que pause/enable vem em segundo:**
- **Frequência alta:** gestor pausa campanhas várias vezes ao dia (fim de semana, fim de promoção, ad_group sub-performante)
- **Risco baixo:** mudança binária e **completamente reversível** (1 comando volta ao estado anterior)
- **Validação do pipeline 6.1:** se a 6.1 estabeleceu o pattern de `mutateResources` + audit log, esta story confirma que o mesmo pattern funciona para campos não-numéricos (status enum) — antes de partir para `create` (mais complexo)
- **Sem threshold:** diferente de budget, não há "+50%" — é binário (ENABLED vs PAUSED)

**Pattern reusado da Story 6.1:**
- Adapter port: extensão de `src/google-ads-api/mutations.ts` (não criar arquivo novo)
- Audit log: mesma estrutura `MutationLogEntry`, com `operation: 'pause_campaign' | 'enable_campaign' | 'pause_ad_group' | 'enable_ad_group'`
- Pre-fetch obrigatório (lê status + nome atuais antes de mutar)
- `--dry-run` mapeia para `validate_only: true` do SDK
- Boundary rule: toda chamada SDK fica em `src/google-ads-api/mutations.ts`

**Sandbox confirmado:** customer-id `5562216599` ("Solaro Marketing e Vendas"). Smoke target: campanha `23478792639` ("[SOL] Rede de pesquisa | Institucional | Porto Alegre") — mesma usada e validada na Story 6.1.

**O que NÃO faz parte desta story:**
- Pausar/reativar `ad` individual (out-of-scope; cobre só campaign + ad_group; ads ficam para 6.5)
- Pausar/reativar `keyword` (cobertura na Story 6.4)
- Bulk pause (múltiplas campanhas em 1 comando — uma campanha por invocação nesta story)
- Recriar campanha `REMOVED` (Google trata como soft delete; reativação não é possível via API — só re-create)
- Schedule-based pause (ex: "pausar à meia-noite") — out of scope

## Risks

| ID | Risco | Probabilidade | Impacto | Mitigação |
|----|-------|--------------|---------|-----------|
| R1 | Pausar campanha em **learning phase** da estratégia de lance quebra performance (Google reinicia ciclo de ~14 dias) | Média | Médio | Warning explícito (não bloqueante) quando pre-fetch detecta `bidding_strategy.last_modified` < 14 dias; cita "interromper learning pode degradar performance" |
| R2 | Race condition — operator pausa no UI ao mesmo tempo que CLI pausa (estado já é o desejado) | Baixa | Baixo | Pre-fetch detecta status atual; se já está em `PAUSED` e comando é `pause`, CLI mostra "já está pausada — nada a fazer" e exit 0 (idempotência) |
| R3 | Status enum diff — Google retorna número (2=ENABLED, 3=REMOVED, 4=PAUSED) mas SDK Opteo tipa como string | Baixa | Baixo | Helper `parseStatusEnum` normaliza string ↔ número; tested com unit |
| R4 | Pausa em conta de **cliente crítico** sem que operator tenha aprovação interna | Média | Médio (relacional) | Documentar como "fora do escopo deste teste técnico" — proteção operacional é responsabilidade do squad/operator; veto técnico não substitui processo |
| R5 | `ad_group` pause/enable é **separado** de `campaign` — operator pode esperar que pausar campanha pause ad_groups, mas não é assim | Média | Baixo | Output explícito após pause campaign: "ad_groups continuam ENABLED — use `pause ad-group <id>` se quiser pausar individualmente"; documentar em README |
| R6 | Veto contra `REMOVED` não detectado em pre-fetch (status REMOVED retornaria erro do SDK confuso) | Baixa | Baixo | Pre-fetch verifica `status === 'REMOVED'` antes de mutar; mensagem PT-BR clara |

   - `--customer-id <id>` (opcional — usa default)

3. Comando `google-ads enable campaign <campaign-id>` com as mesmas flags do AC#2
4. Comando `google-ads pause ad-group <ad-group-id>` e `google-ads enable ad-group <ad-group-id>` com mesmas flags
5. Pre-fetch obrigatório antes de aplicar — para `campaign`:
   - Nome da campanha (para confirmação ao operator)

   - `bidding_strategy.last_modified_time` (para detecção de learning phase)
6. Pre-fetch obrigatório antes de aplicar — para `ad_group`:

   - Nome da campanha pai (contexto)

## Dev Notes

### SDK signature — setCampaignStatus

Diferente de budget (que muta `campaign_budget` entity separada), status é campo direto na entidade `campaign`:

```ts
import { GoogleAdsApi, enums } from 'google-ads-api';

const customer = client.Customer({ customer_id, refresh_token, login_customer_id });

const result = await customer.mutateResources([
  {
    entity: 'campaign',
    resource_name: `customers/${customer_id}/campaigns/${campaignId}`,
    operation: 'update',
    update_mask: { paths: ['status'] },
    status: enums.CampaignStatus.PAUSED, // ou ENABLED
  },
], {
  validate_only: dryRun,
});

// result.results[0].resource_name confirma a entidade atualizada
```

Para `ad_group`, mesmo padrão com `entity: 'ad_group'` e `enums.AdGroupStatus`.

### Status enum (Google's numeric values)

| Valor | Constante SDK | Significado |
|-------|---------------|-------------|
| 2 | `CampaignStatus.ENABLED` | Campanha ativa, servindo |
| 3 | `CampaignStatus.PAUSED` | Pausada, não serve |
| 4 | `CampaignStatus.REMOVED` | Soft-deleted; **não pode ser reativada** |

`AdGroupStatus` segue a mesma numeração. SDK Opteo expõe via `enums` mas a API pode retornar string ("ENABLED") ou número — o helper `parseStatusEnum` normaliza ambos.

### Pre-fetch GAQL — campaign

```sql
SELECT
  campaign.id,
  campaign.name,
  campaign.status,
  campaign.bidding_strategy_type,
  campaign.start_date,
  campaign_criterion_simulation.modified_date_time
FROM campaign
WHERE campaign.id = {campaign_id}
```

Para `last_modified_time` da bidding strategy, pode ser necessário query separada em `bidding_strategy` resource — investigar durante implementação. Se não houver campo limpo, usar `campaign.start_date` como proxy (warning conservador).

### Pre-fetch GAQL — ad_group

```sql
SELECT
  ad_group.id,
  ad_group.name,
  ad_group.status,
  campaign.id,
  campaign.name
FROM ad_group
WHERE ad_group.id = {ad_group_id}
```

### Comando design — `pause/enable <entity> <id>` vs `update status <id> --status PAUSED`

Avaliei duas alternativas:

**Opção A (escolhida):** Comandos dedicados `pause campaign <id>` / `enable campaign <id>`.
- ✅ Verbo intencional — operator lê e entende instantaneamente
- ✅ Combina com `pause ad-group` futuramente `pause ad` (Story 6.5)
- ✅ Output pode ser específico para cada operação (learning warning só em pause)
- ❌ Mais comandos no CLI surface

**Opção B (rejeitada):** Comando genérico `update status <id> --status PAUSED|ENABLED`.
- ✅ Menos surface CLI
- ❌ Verbo "update status" é menos natural que "pause"
- ❌ Não combina bem com semântica de logging (`operation: 'update_status'` é menos auditável que `'pause_campaign'`)
- ❌ Requer mais flags para diferenciar campaign vs ad_group

**Decisão:** Opção A — alinha com convenções de outras CLIs de ads (Facebook ads-cli, Microsoft Ads), e o audit log fica mais explícito por operação.

### Veto Conditions (não fazer)

- ❌ Tentar `pause/enable` em entidade `REMOVED` (Google rejeita e mensagem é confusa)
- ❌ Chamar `mutate` se status atual já é o desejado (desperdício de quota; viola idempotência)
- ❌ Aplicar mutate sem pre-fetch (sem isso, não há diff nem detecção de learning phase)
- ❌ Pausar `ad_group` esperando que pause `ads` ou `keywords` (são entidades separadas — Story 6.4/6.5)
- ❌ Importar `google-ads-api` (npm) fora de `src/google-ads-api/`

## Dev Agent Record

### Execution mode
YOLO autônomo. Pattern de mutação da Story 6.1 era tão bem estabelecido que a implementação foi quase mecânica — exceto pelo BUG do enum descoberto no smoke.

### Decisões técnicas tomadas

1. **`setCampaignStatus`/`setAdGroupStatus` simétricos**: mesmo padrão da SetStatusInput interface; ambos retornam SetStatusResult padronizado. Reduz mental load do CLI consumer.

2. **Handler único `handleStatusMutation`** em pause-enable.ts: parameterizado por operation (pause/enable) + entityType (campaign/ad-group) + entityId. As 4 commands (pause/enable × campaign/ad-group) são wrappers leves desse handler. Reduz duplicação de ~75%.

3. **Idempotência ANTES de pre-fetch da bidding info**: se `status === targetStatus`, exit 0 imediato sem nenhuma chamada de mutate. Economiza quota + UX clara.

4. **Cancellation cria audit log com success=false**: importante para forensics — "operator cancelou o pause da campanha X às 13:38:40" pode ser informação útil.

5. **`requireSimpleConfirm` vs `requireDoubleConfirm` (6.1)**: operação reversível justifica prompt simples s/N. Não vale forçar o operator a digitar frase exata pra pausar campanha que ele pode reativar em 5 segundos.

### Bug descoberto durante smoke (e corrigido)

**Problema:** Story drafted (e código implementado) assumiu o enum CampaignStatus como:
- 2 = ENABLED ✓
- 3 = REMOVED ✗ (INCORRETO)
- 4 = PAUSED ✗ (INCORRETO)

**Realidade (Google Ads API v23, confirmado em `node_modules/google-ads-api/build/src/protos/autogen/enums.d.ts`):**
- 2 = ENABLED ✓
- 3 = PAUSED ✓
- 4 = REMOVED ✓

**Sintoma:** Após pausar a campanha (smoke 2), retornou na próxima verificação como "REMOVED" (que mapeava para 3, mas 3 é PAUSED). Subsequente smoke 3 e 4 falharam com "Não é possível alterar status de campanha removida".

**Fix aplicado:**
1. `normalizeStatus` em `mutations.ts` corrigido
2. `parseStatusEnum` em `status-validator.ts` corrigido
3. Tabela em Dev Notes atualizada
4. Tests do parseStatusEnum atualizados
5. Smoke 3+4 re-rodados ✅

**Lição:** sempre verificar enum values direto no `.d.ts` da SDK, não assumir.
