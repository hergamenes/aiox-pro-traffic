## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** os comandos `google-ads accounts` (listar contas acessíveis) e `google-ads config set-default` (definir conta padrão),
**so that** eu não precise passar `--customer-id` em todo comando e tenha visibilidade clara de quais contas eu posso operar.

## Context

Segunda story do épico `epic-5-google-ads-agent`. Story 5.1 (`auth` + foundations) está **Done** e validada com smoke real-time (PASS). Esta story adiciona dois comandos de leitura/configuração antes do report.

**Por que essa story é a segunda:** o `report` (5.3) precisa de um `customer-id` — ou o usuário passa por argumento, ou usa o default configurado. Para o squad `traffic-google` operar fluidamente, default tem que existir. E pra escolher o default, o usuário precisa ver as opções via `accounts`.

**Dependência crítica:** Story 5.1 Done (módulos `auth/`, `google-ads-api/client.ts`, `errors/`, `config/` já existem).

**O que NÃO faz parte desta story:**
- `report` (5.3)
- Expansão de hierarquia MCC profunda (opcional — MVP só lista flat dos accessibleCustomers)
- Operações mutáveis (`create`, `up`) — Phase 2

## Acceptance Criteria

1. Comando `google-ads accounts` lista contas acessíveis retornadas por `listAccessibleCustomers` (já existe no adapter)
2. Output padrão é tabela com colunas mínimas: `ID`. Se possível enriquecer com `Nome` e `Moeda` via GAQL adicional, fazer (POST-MVP aceitável se complexo)
3. Flag `--format json` emite array JSON `[{"customerId": "1234567890"}]` para parsing em scripts
4. Comando exige `auth status` válido — se inválido, exit 1 com mensagem PT-BR apontando para `auth setup`
5. Comando `google-ads config set-default` é interativo: pergunta `customer-id` (com validação de formato 10 dígitos) e opcionalmente `login-customer-id` (MCC)
6. Valores são persistidos no Keychain (chaves `customer-id` e `login-customer-id` já declaradas na Story 5.1 — só falta o command que as escreve)
7. Comando `google-ads config get-default` exibe o que está salvo (sem mostrar tokens — só customer-id, login-customer-id)
8. Após `config set-default`, executar `auth status` continua passando (sanity check)
9. Módulo `src/config/config-repository.ts` adicionado (mesmo se simples wrapper sobre keychain — para parity com meta-ads pattern e para 5.3 ler default)
10. Testes unitários cobrindo: `accounts` (mock SDK retorna 2-3 customers) e `config set-default` (mock keychain valida persistência); ≥80% coverage nos arquivos novos
11. `npm run lint` clean, `npm run build` sucesso, `--help` mostra `accounts` e `config` registrados
12. Smoke manual: `google-ads accounts` retorna pelo menos a conta `1528041123` (já confirmada na Story 5.1 smoke); `google-ads config set-default` aceita essa conta como default e `auth status` segue verde

### GAQL para enrichment de account

Se quiser enrichment (Nome + Moeda) — query GAQL via adapter port:

```ts
const customer = client.Customer({ customer_id: id, refresh_token });
const rows = await customer.query(`
  SELECT customer.id, customer.descriptive_name, customer.currency_code, customer.status
  FROM customer
  LIMIT 1
`);
// rows[0].customer.{id,descriptive_name,currency_code,status}
```

⚠️ Cada customer requer 1 query. Para conta com MCC que tem 50 contas filhas isso vira 50 queries. Considerar concorrência limitada (Promise.allSettled com p-limit) ou aceitar latência ~1-3s.

**Decisão recomendada:** começar SEM enrichment (só IDs). Adicionar enrichment como Task 1 só se a UX de "lista de IDs nus" for ruim no smoke. PR pode evoluir.

### Config YAML path (parity com meta-ads)

`~/.aiox/google-ads.yaml` (criar dir `~/.aiox/` se não existir; `meta-ads.yaml` já vive lá pelo meta-ads-agent).

> **Alternativa:** persistir tudo no Keychain (incluindo customer-id e login-customer-id, que já tem keys reservadas na Story 5.1). YAML fica como cache opcional. Decisão do @dev qual abordagem é mais limpa — recomendo Keychain-only para MVP (menos arquivos a sincronizar).

### Boundary rule (lembrete)

Apenas `src/google-ads-api/` importa o pacote npm `google-ads-api`. Story 5.1 já estabeleceu — manter.

### Veto Conditions (não fazer)

- ❌ Hardcodar default customer-id
- ❌ Persistir customer-id em arquivo de texto sem ofuscação (se for por YAML, ainda OK — não é segredo, mas Keychain é mais consistente)
- ❌ Quebrar boundary rule (importar `google-ads-api` em accounts.ts ou config.ts)
- ❌ Pular validação de formato (10 dígitos) do customer-id no `set-default`
