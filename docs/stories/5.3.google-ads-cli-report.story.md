## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** o comando `google-ads report` com paridade de contrato ao `meta-ads report` (mesmas options, mesmo schema JSON),
**so that** os agents `campaign-optimizer` e `performance-analyst` do futuro squad possam parsear dados real-time do Google Ads com a mesma lógica que já parseia Meta Ads.

## Context

Terceira e última story do MVP do épico `epic-5-google-ads-agent`. Esta é a **estrela do MVP** — depois dela, `@squad-chief` consegue criar o squad `traffic-google` espelhando o `traffic-meta`.

**Por que essa story é a última de 3:**
- 5.1 (auth) e 5.2 (accounts + config) já foram entregues — adapter port pronto, defaults configurados
- 5.3 só precisa adicionar o command `report` que chama `customer.report({...})` via adapter
- Contrato JSON é declarado pelo @architect (`docs/architecture/google-ads-agent.md` seção 8) e é IGUAL ao do meta-ads para reuso do squad

**Dependência crítica:** Stories 5.1 e 5.2 Done. Smoke da 5.1 já confirmou `customer 1528041123` acessível — esta story usa a mesma conta para smoke.

**O que NÃO faz parte desta story:**
- Mutations (`create`, `up`, `batch`) — Phase 2 (épico futuro)
- Upload de criativos — Phase 2
- Comparação histórica com período anterior (cliente do report faz a diff; squad analyst orquestra) — não precisa estar no CLI
- Dashboard/UI — escopo do squad, não do CLI

## Acceptance Criteria

1. Comando `google-ads report [customer-id]` registrado no CLI
2. Args: `customer-id` opcional (default lido via `config-repository`); se nem default nem arg, exit 1 com mensagem PT-BR pedindo `config set-default` ou passagem por arg
3. Options:
   - `--period <7d|14d|30d>` (default: `7d`)
   - `--from <YYYY-MM-DD>` + `--to <YYYY-MM-DD>` (se um for passado, outro também é obrigatório — validar)
   - `--level <account|campaign|ad_group|ad|keyword>` (default: `campaign`; auto-switch para `ad_group` se `--campaign-id` ou `--tag` forem usados sem `--level` explícito — parity com meta-ads behavior)
   - `--format <table|json>` (default: `table`)
   - `--campaign-id <id>` (filtro server-side via GAQL WHERE)
   - `--tag <substring>` (filtro client-side via `campaign-filter.ts`)
   - `--login-customer-id <mcc>` (override do default — para MCC dinâmico)
4. Adapter: `src/google-ads-api/adapter.ts` exporta `getInsights(InsightsParams): Promise<ParsedMetrics[]>` que monta GAQL e chama `customer.report({...})` via SDK
5. Parser: `src/reporting/insights-parser.ts` converte cada row do Google Ads para `ParsedMetrics` (objeto com schema canônico — ver §8 do arch doc)
6. Schema JSON do output (`--format json`) tem AS MESMAS CHAVES que o `meta-ads report --format json`:
   ```
   { id, name, level, spend, impressions, clicks, ctr, cpc, conversions, cpa, roas, date_range }
   ```
   - `id` é o entity ID na granularidade selecionada (campaign.id, ad_group.id, etc)
   - `name` é o descritivo correspondente
   - `level` é o valor do `--level` selecionado
   - `spend` é `cost_micros / 1_000_000` (BRL ou USD conforme `currency_code` do customer)
   - `cpa` é `spend / conversions` (omitido se `conversions === 0`)
   - `roas` é `conversions_value / spend` (omitido se `conversions_value === 0` ou ausente)
   - `date_range` é `{ from: 'YYYY-MM-DD', to: 'YYYY-MM-DD' }`
7. Formatter: `src/reporting/report-formatter.ts` formata `ParsedMetrics[]` em table OU json (port do pattern meta-ads)
8. Filter: `src/reporting/campaign-filter.ts` aplica `--tag` como substring match em `name` (case-insensitive, parity meta-ads)
9. Veto conditions:
   - `auth status` válido (exit 1 + PT-BR pointer para `auth setup` se inválido)
   - Datas válidas (ISO 8601 YYYY-MM-DD) se `--from`/`--to` usados; se `--from` sem `--to` ou vice-versa, exit 1
   - Customer-id resolvido (arg OU default); se nenhum, exit 1
10. Boundary rule respeitada — apenas `src/google-ads-api/` importa SDK
11. Testes unitários:
    - `insights-parser.test.ts` com fixtures de rows Google (mínimo 4 cenários: campaign normal, com `conversions_value`, sem conversions, com cost_micros zero)
    - `campaign-filter.test.ts` (port do meta-ads)
    - `report-formatter.test.ts` (table com colWidths corretos + json com keys idênticas ao schema)
    - `adapter.test.ts` com mock SDK retornando 2-3 rows
    - Coverage ≥80% nos arquivos novos
12. `npm run lint` clean, `npm run build` sucesso; smoke manual em conta real:
    - `google-ads report --period 7d --level campaign --format json` retorna array (mesmo que vazio se não tiver gastado nos 7d) — não pode crashar
    - `google-ads report --from 2026-05-01 --to 2026-05-07 --level ad_group --format json` funciona com date range custom

| meta-ads `--level` | google-ads `--level` | Google entity |
|---------------------|-----------------------|---------------|
| account | account | (no entity — query in customer scope) |
| campaign | campaign | `FROM campaign` |
| adset | ad_group | `FROM ad_group` |
| ad | ad | `FROM ad_group_ad` |
| — (n/a) | keyword | `FROM ad_group_criterion WHERE ad_group_criterion.type = 'KEYWORD'` |

## Dev Agent Record

### Execution mode
Semi-autonomous (per @po recommendation interactive was suggested — usei semi-auto com checkpoints só nos pontos críticos: schema parity test + smoke).

### Decisões técnicas tomadas
1. **Schema canônico simplificado vs meta-ads:** O `meta-ads-agent` usa keys level-nominais (`campaignName`, `adsetId`, ...) com 22+ métricas; nosso `ParsedMetrics` usa shape level-agnostic (`{id, name, level, ...12 keys}`) para suportar 5 levels uniformemente. Documentado no schema-parity.test.ts que strict parity NÃO é viável; squad consumers que comparam cross-platform precisam de normalizer adapter. **Esta decisão diverge da AC #6 literal mas é arquiteturalmente correta** — registro para QA discutir.
2. **Currency lookup separado:** `getInsights` faz 1 query extra inicial (`SELECT customer.currency_code FROM customer LIMIT 1`) para obter moeda da conta. Falha gracefully (currency vira `undefined`, parser ainda funciona).
3. **Date range computed locally:** Para `period: 7d/14d/30d`, o `computeDateRange` calcula `from`/`to` localmente em ISO format para preencher o `date_range` do output (Google API não retorna esse range explicitamente quando usamos `DURING LAST_N_DAYS`).
4. **Error handling melhorado mid-flight:** Durante smoke, descobri que `Object.values(error_code)[0]` precisava virar loop (Google Ads SDK pode aninhar codes em diferentes keys). Adicionado fallback de substring match na mensagem como rede de segurança.
5. **Sem retry/backoff:** Aceito MVP — usuário pode retry manualmente. Adicionar se UX virar problema.
