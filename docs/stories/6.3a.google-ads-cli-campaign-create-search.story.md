## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** o comando `google-ads create campaign-search` que cria uma nova campanha do tipo Search (Rede de Pesquisa) via CLI, gerando atomicamente o `CampaignBudget` + `Campaign` em status PAUSED,
**so that** eu possa iniciar a criação de campanhas Search sem abrir o Google Ads UI — com a campanha já preparada para receber ad_group + keywords (Story 6.4) e ads (Story 6.5), e com vetos que previnem auto-enable acidental (burn protection) e runaway-spend em batch operations.

## Context

Terceira story do **Epic 6 — Google Ads CLI Mutations** (`docs/stories/epics/epic-6-google-ads-mutations/EPIC.md`). Stories 6.1 (update budget/bidding) e 6.2 (pause/enable) entregaram as **mutações de campanhas existentes**. Esta story inicia o **CRUD completo** ao adicionar a primeira operação `CREATE`.

**Por que Search é o primeiro tipo de campanha criado:**
- **Tipo mais comum:** ~70% das campanhas em contas Solaro são Search (intent-based, conversão direta)
- **Hierarquia tradicional e previsível:** Campaign → Ad Group → Ad → Keyword (vs Performance Max que usa asset_groups)
- **Modelo de bidding bem documentado:** Maximize Conversions / Target CPA / Manual CPC — sem dependências de AI signals
- **Risco controlável:** criada em PAUSED por default — sem burn enquanto operator monta ad_group + keywords + ads
- **Destrava `*publish` autônomo do squad para Search** (caso de uso mais frequente)

**Decisão arquitetural crítica — escopo de 6.3a vs 6.4 vs 6.5:**

Optamos por criar **apenas Campaign + CampaignBudget** nesta story usando `mutateResources` atômico com temporary resource_names. As demais sub-stories preenchem a hierarquia:

| Story | Cria | Status pós-execução |
|-------|------|---------------------|
| **6.3a** (esta) | `CampaignBudget` + `Campaign` (status=PAUSED) | Campanha sem ad_group; não roda; não gasta |
| **6.4** | `AdGroup` + `KeywordCriterion` (≥1) | Campanha + ad_group + keywords; ainda PAUSED |
| **6.5** | `Ad` (RSA — Responsive Search Ad) | Hierarquia completa; ainda PAUSED |
| **6.2** (`*enable`) | — | Operator decide explicitamente ENABLE → começa a rodar/gastar |

**Por que NÃO fazer tudo de uma vez em 6.3a:**
- Cada tipo de mutação tem veto/UX próprios (anti-bid-shock em keywords, validação de RSA assets em ads) — misturar inflaria a story
- Failure em qualquer etapa intermediária deixaria estado inconsistente — separar permite retry granular
- Permite shipping incremental de valor

**Por que CRIAR PAUSED por default (não negociável):**
- Campanha sem ad_group/ad é tecnicamente inválida no Google — não rodaria mesmo se ENABLED. Mas após 6.4+6.5, fica válida — se estiver ENABLED por engano, começa a gastar imediatamente
- Operator humano DEVE chamar `*enable` (Story 6.2) explicitamente quando estiver pronto para spend
- Padrão seguro by-default vence padrão "pronto pra rodar" — burn é irreversível

**Sandbox confirmado:** customer-id `5562216599` ("Solaro Marketing e Vendas") — sub-conta da MCC, ENABLED, em BRL, Standard Access. Mesma sandbox das stories 6.1 + 6.2.

**O que NÃO faz parte desta story:**
- Display campaigns (Story 6.3b)
- Performance Max campaigns (Story 6.3c)
- Ad group creation (Story 6.4)
- Keyword management (Story 6.4)
- Ad creation — RSA/RDA (Story 6.5)
- Auto-enable da campanha criada (proibido — Story 6.2 faz isso explicitamente)
- Conversion tracking setup (out of epic)
- Audience targeting / location targeting customizado (defaults da conta serão usados)
- Negative keywords (out of 6.3a)

## Acceptance Criteria

1. Novo subcomando `google-ads create` registrado no CLI (parent de operações de criação; sub-stories 6.3b/6.3c/6.4/6.5/6.6 adicionarão mais subcomandos)
2. Subcomando `google-ads create campaign-search` aceita:
   - `--name <text>` (obrigatório, max 255 chars — limite do Google)
   - `--daily <amount>` (obrigatório, budget diário na moeda da conta; aceita "R$ 30", "30", "30,00", "30.00")
   - `--bidding <strategy>` (default: `maximize_conversions`; valores aceitos: `maximize_conversions`, `target_cpa`, `target_roas`, `manual_cpc`, `maximize_conversion_value`)
   - `--target <value>` (obrigatório quando strategy é `target_cpa` ou `target_roas`; CPA em currency unit ou ROAS como decimal ex: 2.5)
   - `--start-date <YYYY-MM-DD>` (opcional, default = hoje na timezone da conta)
   - `--customer-id <id>` (opcional, usa default)
   - `--login-customer-id <id>` (opcional, para sub-contas de MCC — flag aditiva como em 6.1)
   - `--dry-run` (validate_only=true; não cria nada real, apenas valida shape do mutate)
   - `--max-session-budget <amount>` (default R$ 500; limite de soma de `--daily` em sessão; configurável)
   - `--force-max-session-budget` (override explícito do limite — exigido quando ultrapassado)
3. Pre-fetch obrigatório antes de mutar — CLI faz GAQL para ler:
   - `customer.currency_code` + `customer.time_zone` + `customer.manager` (não pode ser MCC — reusa veto da Story 5.3)

### SDK signature — mutateResources atômico com temp IDs

```ts
import { GoogleAdsApi, resources, enums, MutateOperation } from 'google-ads-api';

const customer = client.Customer({ customer_id, refresh_token, login_customer_id });

const operations: MutateOperation<resources.ICampaignBudget | resources.ICampaign>[] = [
  // 1. CampaignBudget — temp resource_name -1
  {
    entity: 'campaign_budget',
    operation: 'create',
    resource: {
      resource_name: `customers/${customerId}/campaignBudgets/-1`,
      name: `${name} Budget`,
      amount_micros: dailyMicros,
      delivery_method: enums.BudgetDeliveryMethod.STANDARD,
      explicitly_shared: false,
    },
  },
  // 2. Campaign — referencia campaignBudget pelo temp resource_name -1
  {
    entity: 'campaign',
    operation: 'create',
    resource: {
      name,
      advertising_channel_type: enums.AdvertisingChannelType.SEARCH,
      status: enums.CampaignStatus.PAUSED, // NUNCA ENABLED nesta story
      campaign_budget: `customers/${customerId}/campaignBudgets/-1`, // resolve via temp
      network_settings: {
        target_google_search: true,
        target_search_network: true,
        target_content_network: false,
        target_partner_search_network: false,
      },
      start_date: startDateYYYYMMDD,
      // Bidding strategy — exatamente um destes campos
      ...buildBiddingFields(bidding, targetMicros),
    },
  },
];

const result = await customer.mutateResources(operations, {
  validate_only: dryRun, // true para --dry-run
  partial_failure: false, // atomic — tudo ou nada
});

// result.mutate_operation_responses[0] = budget result (resource_name)
// result.mutate_operation_responses[1] = campaign result (resource_name)
```

### Temporary resource_names — convenção Google Ads API

- IDs negativos (`-1`, `-2`, `-3`) dentro de uma única chamada `mutateResources` funcionam como "placeholders"
- Google resolve atomicamente: se a request inteira passar, atribui IDs reais e substitui as cross-references
- Se qualquer operação falhar, nenhuma é aplicada (atomic)
- Devem ser referenciados via path completo: `customers/{customer_id}/campaignBudgets/-1`

### Por que PAUSED por default — não-negociável

- Operator humano deve ter checkpoint **explícito** entre criar e gastar dinheiro
- Mesmo após Stories 6.4+6.5 completarem hierarquia, `*enable` (Story 6.2) é a única forma de habilitar — força revisão final
- Se default fosse ENABLED, criar 24 campanhas em batch poderia iniciar burn de R$ 500/dia × 24 = R$ 12.000/dia acidentalmente

### Por que single-confirm (não double-confirm)

- Criar campanha PAUSED não causa spend imediato → risco menor que +50% budget update da Story 6.1
- Veto principal de spend acontece mais tarde, em `*enable` (Story 6.2)
- Anti-runaway batch (`--max-session-budget`) cobre o caso de loop acidental
- UX simples > UX defensiva quando risco é bounded

### Veto Conditions (não fazer)

- ❌ Aplicar `mutateResources` sem pre-fetch de currency_code / time_zone (R3)
- ❌ Aceitar `--status enabled` ou similar flag (proibido — R6 veto, Story 6.2 é a única autoridade)
- ❌ Criar Budget como `explicitly_shared: true` (compartilhar budget entre campanhas é decisão separada — out of scope)
- ❌ Network settings = `target_content_network: true` por default (isso seria mistura Search + Display — fora do escopo de "Search puro")
- ❌ Pular check de campanha-com-mesmo-nome (R5 — Google rejeitaria com erro críptico)
- ❌ Logar payload completo de mutate no audit log com PII (limitar a IDs + valores numéricos + nome — mesmo padrão da Story 6.1)
- ❌ Importar `google-ads-api` (npm) fora de `src/google-ads-api/` (boundary rule)
