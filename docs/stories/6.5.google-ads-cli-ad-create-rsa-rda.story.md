## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** os comandos `google-ads create ad rsa <ad-group-id>` e `google-ads create ad rda <ad-group-id>` que criam Responsive Search Ads (RSA) e Responsive Display Ads (RDA) dentro de ad_groups existentes via CLI,
**so that** eu possa publicar criativos em campanhas Search e Display sem abrir o Google Ads UI — com validação de char limits client-side e veto conditions que previnem rejeição posterior por policy ou type mismatch.

## Context

Quinta story do **Epic 6 — Google Ads CLI Mutations** (`docs/stories/epics/epic-6-google-ads-mutations/EPIC.md`), parte do **Tier 3 — Mídia e Tipos Avançados**. Vem após Story 6.4 (ad_group + keywords) que cria a hierarquia onde os ads vão morar. Story 6.6 (asset upload) é dependência soft para o smoke de RDA — RSA não precisa.

**Por que essa story:**
- Sem ads, ad_groups são containers vazios — campanha não roda
- RSA é o formato padrão (e quase único) de Search desde 2022; RDA é o padrão de Display
- Replicar 1 ad em 5 contas via UI demora 15-25 min; via CLI batch é ~30s
- Validação client-side de char limits previne erros caros (rejeições pós-submissão são lentas)

**Decisão arquitetural — Asset references para RDA:**
Google Ads moveu a criação de RDA para o modelo de **Asset references** (apontar para assets pré-uploaded em vez de enviar bytes inline). Esta story assume que assets de imagem já foram uploaded (via Story 6.6 OU manualmente pelo UI antes). RSA não tem essa dependência — todo o conteúdo é texto.

**Sandbox confirmado:** customer `5562216599`. Token Standard Access. Adapter port: estender `src/google-ads-api/mutations.ts`.

**O que NÃO faz parte desta story:**
- Upload de imagens/vídeos (Story 6.6)
- App Ads / Shopping Ads / Video Ads / Performance Max asset_group ads (out of epic)
- Edição de ads existentes — Google trata ads como imutáveis; muda = delete + create (não está nesta story)
- Preview de ad antes de criar (UI feature; CLI mostra texto formatado)
- A/B test/experiment configuration

## Risks

| ID | Risco | Probabilidade | Impacto | Mitigação |
|----|-------|--------------|---------|-----------|
| R1 | **Ad type mismatch com tipo de campanha** — operator tenta RSA em ad_group Display ou RDA em ad_group Search | Média | Alto (API rejeita ou cria órfão) | Pre-fetch lê `ad_group.campaign.advertising_channel_type` e veto se incompatível; mensagem PT-BR explícita |
| R2 | Char limits violados (headline >30, description >90, etc) | Alta | Médio (rejeição API) | Validação client-side ANTES de chamar API; lista entradas inválidas no output com índice + char count |
| R3 | Asset references para RDA falham se assets não estão prontos (dep Story 6.6) | Média | Médio | Pre-fetch valida que asset_ids existem via `SELECT asset.id, asset.type FROM asset WHERE asset.id IN (...)`; veto se algum não encontrado |
| R4 | Policy violations no texto (claims proibidos, capitalização excessiva, etc) — Google rejeita silenciosamente | Média | Médio | Aceito — Google só roda policy check pós-create; ad ficará em status "DISAPPROVED"; documentar como nota; CLI sugere consulta ao Policy Center no output |
| R5 | Pinning de headlines reduz capacidade ML de otimização (Google deprioriza ad) | Baixa | Baixo | Warning quando `--pinned-headline-*` é usado: "Pinning reduz otimização ML; use com moderação" |
| R6 | RSA exige mínimo 3 headlines + 2 descriptions; operator esquece e API rejeita | Média | Baixo | Validação client-side de counts mín/máx por formato; mensagem clara antes de chamar API |
| R7 | `final_url` não HTTPS (Google requer HTTPS desde 2018) | Baixa | Médio | Validação client-side: regex `^https://`; veto se HTTP simples |

## Acceptance Criteria

1. Novo subcomando `google-ads create ad rsa <ad-group-id>` registrado sob o grupo `create` (parent já criado em 6.3a)
2. `google-ads create ad rsa <ad-group-id>` aceita:
   - `--final-url <url>` (required, deve começar com `https://`)
   - `--headlines <text>...` (3-15 entries, flag repetível ou string com `|` como separador)
   - `--descriptions <text>...` (2-4 entries)
   - `--path1 <text>`, `--path2 <text>` (opcionais, máx 15 chars cada)
   - `--pinned-headline-1 <text>` (opcional, pinha headline na posição 1)
   - `--customer-id <id>`, `--login-customer-id <id>`, `--dry-run` (padrão de 6.1)
3. Novo subcomando `google-ads create ad rda <ad-group-id>` aceita:
   - `--final-url <url>` (required, HTTPS)
   - `--headlines <text>...` (1-5 entries, máx 30 chars cada)
   - `--long-headline <text>` (required, máx 90 chars)
   - `--descriptions <text>...` (1-5 entries, máx 90 chars cada)
   - `--business-name <text>` (required, máx 25 chars)
   - `--logo-asset-id <id>` (required, single)
   - `--marketing-image-asset-id <id>...` (1+ entries, flag repetível)
   - `--square-marketing-image-asset-id <id>...` (opcional, 1+ entries)
   - `--customer-id <id>`, `--login-customer-id <id>`, `--dry-run`
4. Pre-fetch obrigatório: antes de criar, CLI faz `customer.query` para ler:
   - `ad_group.id`, `ad_group.name`, `ad_group.status`, `ad_group.type`
   - `ad_group.campaign` (resource name) + `campaign.advertising_channel_type` (SEARCH | DISPLAY | etc)
   - Para RDA: validar asset IDs informados via `SELECT asset.id, asset.type, asset.name FROM asset WHERE asset.id IN (...)`
5. Veto — Ad type mismatch (R1):
   - `create ad rsa` exige `campaign.advertising_channel_type = SEARCH` — caso contrário exit 1 com mensagem PT-BR ("RSA só pode ser criado em campanhas Search; ad_group {id} pertence a campanha {type}")
   - `create ad rda` exige `campaign.advertising_channel_type = DISPLAY` — caso contrário exit 1 similar
6. Veto — Char limits (R2):
   - RSA: cada headline ≤ 30 chars; cada description ≤ 90 chars; path1/path2 ≤ 15 chars
   - RDA: short headlines ≤ 30; long headline ≤ 90; descriptions ≤ 90; business_name ≤ 25
   - Validação ANTES de chamar API; output lista índice + char count das entradas inválidas; exit 1 sem mutar
7. Veto — Counts mínimo/máximo (R6):
   - RSA: 3 ≤ headlines.count ≤ 15; 2 ≤ descriptions.count ≤ 4
   - RDA: 1 ≤ headlines.count ≤ 5; 1 ≤ descriptions.count ≤ 5; 1+ marketing-image-asset-id
   - Se fora dos limites, exit 1 com mensagem PT-BR
8. Veto — Asset references (R3, somente RDA):
   - Se algum `--logo-asset-id` ou `--marketing-image-asset-id` não for encontrado no customer, exit 1 listando os IDs ausentes
   - Aceita assets de qualquer tipo (Google valida tipo no submit) — apenas confirma existência
9. Veto — final_url HTTPS (R7):
   - Se `--final-url` não começa com `https://`, exit 1 com mensagem "Google Ads requer HTTPS em final_url; recebi {url}"
10. Status default do ad criado: `PAUSED` (não publica automaticamente; operator precisa habilitar via `enable` da Story 6.2 OU via UI)
11. Warning não-bloqueante (R5):
    - Se `--pinned-headline-1` é usado, mostra warning amarelo: "⚠️ Pinning de headline reduz otimização ML do Google; ad pode performar pior. Use com moderação."
12. Confirmation UX antes de criar (RSA exemplo):
    ```
    📋 Criar Responsive Search Ad
    ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    Ad Group:        Brand - PT (123456789)
    Campanha:        [SOL] Rede de pesquisa | Institucional (23478792639)
    Tipo:            SEARCH ✓
    Conta:           5562216599 (Solaro Marketing e Vendas)

    Headlines (5):
      1. Marketing Digital Solaro       (28/30 chars) [PINNED 1]
      2. Resultados em 30 Dias          (24/30)
      3. Especialistas em Tráfego       (26/30)
      4. Atendimento Premium            (21/30)
      5. Solicite Diagnóstico Grátis    (29/30)

    Descriptions (2):
      1. Aumente suas vendas com gestão de tráfego pago Google e Meta. (61/90)
      2. Time certificado, relatórios semanais e ROI mensurável.       (57/90)

    Display URL:     example.com/marketing/digital
      ├ Final URL:   https://example.com/landing
    ```

13. Output pós-criação: mostra `resource_name` retornado + link direto ao Google Ads UI para verificação + nota sobre policy review ("Google fará revisão de policy nas próximas horas; status pode mudar para DISAPPROVED se houver violação — consulte ads.google.com/policy")
14. Audit log em `~/.aiox/google-ads-mutations.log` (JSON Lines):
    - RSA: `operation: 'create_rsa'`, snapshot dos headlines/descriptions/paths
    - RDA: `operation: 'create_rda'`, snapshot de headlines/long_headline/descriptions/business_name/asset_ids
    - Demais campos padrão (timestamp, customer_id, ad_group_id, resource_name, dry_run, success)
15. Boundary rule respeitada — toda lógica de SDK fica em `src/google-ads-api/mutations.ts` (estende o arquivo de 6.1-6.4)
16. Testes unitários (≥80% cobertura nos arquivos novos):

```ts
const customer = client.Customer({ customer_id, refresh_token, login_customer_id });
```

### Pre-fetch GAQL — ad_group + campaign type

```sql
SELECT
  ad_group.id,
  ad_group.name,
  ad_group.status,
  ad_group.type,
  ad_group.campaign,
  campaign.id,
  campaign.name,
  campaign.advertising_channel_type
FROM ad_group
WHERE ad_group.id = {ad_group_id}
```

`campaign.advertising_channel_type` retorna enum: `SEARCH`, `DISPLAY`, `SHOPPING`, `VIDEO`, `MULTI_CHANNEL` (PMax), etc. Usar para o veto AC#5.

### Pre-fetch GAQL — asset existence (RDA)

```sql
SELECT asset.id, asset.type, asset.name
FROM asset
WHERE asset.id IN ({list_of_ids})
```

Comparar IDs retornados com IDs informados → calcular `missing[]`.

### Char limits — referência rápida

| Formato | Campo | Limite |
|---------|-------|--------|
| RSA | headline | 30 |
| RSA | description | 90 |
| RSA | path1 / path2 | 15 |
| RDA | short headline | 30 |
| RDA | long_headline | 90 |
| RDA | description | 90 |
| RDA | business_name | 25 |

Counts:
- RSA: 3-15 headlines, 2-4 descriptions
- RDA: 1-5 headlines, 1 long_headline, 1-5 descriptions, 1+ marketing_image_asset_ids

### Validação client-side (estratégia)

Validar TUDO antes de chamar API:
1. Counts (cardinalidade)
2. Char limits por item
3. HTTPS no final_url
4. Para RDA: asset_ids não-vazios na chamada (existência verificada via pre-fetch no Task 5)

Output dos erros deve ser **listado** (não para no primeiro), para operator corrigir tudo de uma vez:

```
❌ Validação RSA falhou (3 erros):
   • Headline 4: 'Aumente suas vendas com gestão de tráfego pago' tem 47 chars (máx 30)
   • Descriptions: encontrei 1, mínimo é 2
   • final_url: 'http://example.com' precisa ser HTTPS
```

### Veto Conditions (não fazer)

- ❌ Criar RSA em ad_group de campanha Display (e vice-versa) — sempre veto antes de mutar
- ❌ Aceitar `--final-url http://...` (sem S) — Google rejeita; cliente já valida
- ❌ Mutate sem pre-fetch — sem isso, não sabemos campaign type nem nomes para o preview
- ❌ Status default ENABLED — sempre PAUSED, operator habilita explicitamente depois
- ❌ Logar refresh_token / OAuth secrets no mutation log (apenas IDs + texto público dos ads)
- ❌ Pular validação de asset existence em RDA — referência inválida vira erro confuso da API
- ❌ Importar `google-ads-api` (npm) fora de `src/google-ads-api/` (boundary rule da 5.1)
