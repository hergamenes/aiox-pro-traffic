## Story

**As a** gestor de tráfego operando o squad `traffic-google`,
**I want** os comandos `google-ads create ad-group` e `google-ads keyword add/remove/update-bid` que permitem adicionar grupos de anúncios em campanhas existentes e gerenciar keywords (com match type + bid) via CLI,
**so that** eu possa transformar campanhas Search criadas pela Story 6.3a em campanhas **operacionais e veiculáveis** — palavras-chave são o coração de qualquer campanha Search e sem elas nada aparece no leilão.

## Context

Quarta story do **Epic 6 — Google Ads CLI Mutations** (`docs/stories/epics/epic-6-google-ads-mutations/EPIC.md`). Segue o pipeline:

- **Story 6.1 (Done)** — estabeleceu o padrão de mutações (`mutations.ts`, pre-fetch, anti-runaway, audit log)
- **Story 6.2 (Done)** — pause/enable em `campaign` (e potencialmente `ad_group` — a confirmar no escopo dela)
- **Story 6.3a (Done)** — criação de campanhas Search **sem ad_groups** (apenas o shell `campaign` + `campaign_budget`)
- **Story 6.4 (esta)** — fecha o ciclo Search: cria `ad_group` dentro da campanha + adiciona/remove/ajusta `keywords`

**Por que esta é a story que "destrava" o Search:**
Uma campanha Search sem ad_groups + keywords é inerte — não aparece em nenhum leilão. Story 6.3a deixou a campanha pausada e vazia; 6.4 a torna realmente publicável. Sem 6.4, o `*publish` do squad `traffic-google` ainda precisa do Google Ads UI para a etapa final.

**Decisão arquitetural — escopo deste épico:**
- Search: **prioridade máxima** (escopo desta story)
- Display: ad_groups Display têm conceito diferente (orientado a placement/audience, não keyword) — **fora do escopo desta story**, pode entrar em 6.4b futura se necessário
- Performance Max: **não tem ad_groups** (usa asset_groups) — fora de escopo total
- Negative keywords: **fora do escopo** (recurso separado `customer_negative_keyword` + `ad_group_criterion` com `negative: true`); pode entrar em story 6.4c futura

**Sandbox confirmado:** customer-id `5562216599` ("Solaro Marketing e Vendas"). Campanha Search alvo do smoke: `23478792639` ("[SOL] Rede de pesquisa | Institucional | Porto Alegre"), já usada nas Stories 6.1 e 6.2.

**Token Standard Access** — todas as mutações de `ad_group` e `ad_group_criterion` autorizadas.

**O que NÃO faz parte desta story:**
- Criar campanha (Story 6.3a)
- Ad_group de Display/PMax (fora de escopo)
- Negative keywords (sem demanda imediata)
- Criar ads (RSA/RDA) dentro do ad_group (Story 6.5)
- Audience targeting no ad_group (out of epic)
- Bulk import de keywords via CSV (futuro)

## Complexity Estimate

| Métrica | Valor |
|---------|-------|
| T-shirt size | **M** (Medium) |
| Story points (Fibonacci) | **5** |
| Estimativa de tempo @dev | 1-2h |
| Risk-adjusted upper bound | 3h (se bid-shock UX + match-type validation exigir polimento) |

**Justificativa:** Escopo amplo (1 entity para ad_group + 3 sub-operações para keyword) mas todas seguem o padrão já estabelecido pela 6.1 (pre-fetch → diff → confirm → mutate → log). Carry-over de `calculateBudgetDelta` (renomeado para uso polimórfico) e `requireDoubleConfirm` economiza tempo. O risco principal está em validação de keyword text e detecção de bidding strategy automatizada (warning).

## Risks

| ID | Risco | Probabilidade | Impacto | Mitigação |
|----|-------|--------------|---------|-----------|
| R1 | **Add keyword em campanha Display/PMax** quebra com erro críptico do SDK | Média | Médio | Pre-fetch lê `campaign.advertising_channel_type`; veto explícito antes de chamar mutate se não for SEARCH |
| R2 | **Update bid em campanha com bidding automatizado** (target_cpa/target_roas/maximize_conversions): bid é ignorado, operator pensa que aplicou | Alta | Médio | Pre-fetch lê `campaign.bidding_strategy_type`; warning explícito "lance é informacional — algoritmo decide"; flag `--force` para suprimir o warning |
| R3 | **Keyword text inválido** (>80 chars, leading/trailing whitespace, caracteres especiais não suportados) | Média | Baixo | Validação client-side antes do mutate: max 80 chars, trim automático, regex de caracteres permitidos por match_type |
| R4 | **Negative keyword conflita com positive keyword existente** (já tem "tênis nike" como negative no ad_group, tenta adicionar como positive) | Baixa | Baixo | Como negative keywords estão fora de escopo desta story, conflito não é detectado aqui — Google retorna erro 4xx, CLI exibe mensagem PT-BR genérica e linka docs |
| R5 | **Match type ambíguo no input** — operator passa "tênis nike" sem flag e CLI assume BROAD (default agressivo) | Média | Médio | Default explícito = `BROAD`; output mostra match type efetivo no diff; comando exibe nota "match_type=BROAD (default)" quando flag omitida |
| R6 | **Bid shock** — operator aumenta bid de R$ 1,00 → R$ 10,00 acidentalmente em update-bid | Média | **Crítico financeiro** | Carry-over do veto +50% da 6.1 via helper polimórfico `calculatePercentDelta`; double-confirm com frase exata |
| R7 | **Criterion ID inválido / não existe** no remove ou update-bid | Baixa | Baixo | Pre-fetch tenta ler o criterion antes de mutate; se 404 da API, mensagem PT-BR clara "keyword não encontrado — confira ID via report --level keyword" |

### Atomic mutateResources — update bid

```ts
const operations = [
  {
    entity: 'ad_group_criterion',
    resource_name: `customers/${customer_id}/adGroupCriteria/${ad_group_id}~${criterion_id}`,
    operation: 'update',
    update_mask: { paths: ['cpc_bid_micros'] },
    cpc_bid_micros: newBidMicros,
  },
];
```

> **Atenção:** o `resource_name` de `ad_group_criterion` usa formato composto `{ad_group_id}~{criterion_id}` — diferente de outras entidades. Pre-fetch deve retornar tanto `ad_group_id` quanto `criterion_id` para reconstruir corretamente.

### Por que ad_group_criterion (não keyword) é a entidade

Google modela keyword como **um caso particular de `ad_group_criterion`** — outros tipos de criterion são placement, user_list, gender, age_range, etc. Por isso o resource é `ad_group_criterion` com sub-campo `keyword.text` + `keyword.match_type`. Quando lemos via GAQL, filtramos por `ad_group_criterion.type = 'KEYWORD'`.

### Bidding strategy — quando o bid de keyword importa

| Strategy | Lance de keyword é usado? |
|----------|---------------------------|
| `MANUAL_CPC` | **Sim** — bid direto vai pro leilão |
| `MAXIMIZE_CONVERSIONS` | Não — algoritmo decide cada lance |
| `TARGET_CPA` | Não — algoritmo otimiza para CPA alvo |
| `TARGET_ROAS` | Não — algoritmo otimiza para ROAS alvo |
| `MAXIMIZE_CONVERSION_VALUE` | Não |
| `MANUAL_CPM` / `MANUAL_CPV` | Específicos de Video/Display — fora de escopo |

**Decisão de UX:** sempre aceitar `--cpc-bid` no input (para compat futura quando operator migrar strategy), mas warning explícito se for ignorado.

### Negative keywords

**Fora de escopo.** Negative keywords usam o mesmo resource `ad_group_criterion` mas com flag `negative: true`. Implementação seria simétrica. Decisão de adiamento porque (a) gestor mexe mais com positive keywords; (b) negative keyword tem regras adicionais de conflito com positive (mesma palavra como positive + negative = erro). Story 6.4c futura se demanda surgir.

### Bulk import de keywords

**Fora de escopo.** UI suporta importar CSV de keywords. CLI poderia ter `keyword add-batch <ad-group-id> --file keywords.csv` — útil para campanhas grandes. Decisão de adiamento porque o smoke deste épico usa volume pequeno (3-5 keywords/ad_group). Story 6.4d futura se squad pedir.
